## 1. 重试机制概述

系统设置项 `RetryTimes` 控制最大重试次数（默认 `0` 表示不重试）。设为 `N` 时，一次用户请求最多执行 **N+1 次上游调用**（1 次初始 + N 次重试）。

**核心原则：重试优先切换渠道（按优先级降级），而不是在同一渠道内轮换密钥。**

代码位置：`controller/relay.go:189`

```go
for ; retryParam.GetRetry() <= common.RetryTimes; retryParam.IncreaseRetry() {
    channel, channelErr := getChannel(c, relayInfo, retryParam)
    // ... 执行请求 ...
    if newAPIError == nil { return } // 成功
    willRetry := shouldRetry(c, newAPIError, common.RetryTimes-retryParam.GetRetry())
    if !willRetry { break }
}
```

## 2. 重试流程详解

```
用户请求
  │
  ▼
Distribute() 中间件选择初始渠道（最高优先级，加权随机）
  │
  ▼
retry=0: 使用中间件选定的渠道 + 该渠道的 GetNextEnabledKey()
  │
  ├── 成功 → 返回结果
  │
  ├── 失败 → shouldRetry() 判断是否重试
  │     │
  │     ├── 不重试 → 返回错误
  │     │
  │     └── 重试 → processChannelError() 处理错误（可能禁用密钥/渠道）
  │                │
  │                ▼
  │           retry=1: CacheGetRandomSatisfiedChannel(retry=1)
  │             → 选择次高优先级的渠道
  │             → 该渠道调用 GetNextEnabledKey()
  │                │
  │                ├── 成功 → 返回结果
  │                └── 失败 → 继续重试...
  │
  ▼
retry=N: 到达 RetryTimes 上限，返回最后一次错误
```

每次重试都会：
1. 调用 `CacheGetRandomSatisfiedChannel(retry)` 选择新渠道
2. 调用 `SetupContextForSelectedChannel()` 设置渠道上下文
3. 在 `SetupContextForSelectedChannel` 内调用 `channel.GetNextEnabledKey()` 选择密钥

## 3. 渠道选择策略：优先级梯度降级

代码位置：`model/channel_cache.go:96-191`

### 3.1 核心算法

```go
// 1. 收集所有支持该模型的渠道的唯一优先级
// 2. 降序排列：[100, 50, 10]
sort.Sort(sort.Reverse(sort.IntSlice(sortedUniquePriorities)))

// 3. retry 值作为优先级梯度的索引
if retry >= len(uniquePriorities) {
    retry = len(uniquePriorities) - 1  // 钳制到最低优先级
}
targetPriority := sortedUniquePriorities[retry]

// 4. 在目标优先级的所有渠道中，按权重随机选择
```

### 3.2 优先级梯度映射

| retry 值 | 选择的优先级层 |
|----------|---------------|
| 0 | 最高优先级（如 100） |
| 1 | 次高优先级（如 50） |
| 2 | 第三优先级（如 10） |
| >= 梯度总数 | 钳制到最低优先级，反复选择 |

### 3.3 同优先级内的加权随机

当同一优先级有多个渠道时，按渠道权重（weight）做加权随机选择：

- 权重越大，被选中概率越高
- 所有权重为 0 时，每个渠道等概率
- 权重平均值 < 10 时，乘以 100 平滑处理

## 4. 多密钥机制详解

代码位置：`model/channel.go:128-213`

### 4.1 开启多密钥

渠道配置中将 `IsMultiKey` 设为 `true`，密钥以换行符 `\n` 分隔填入 Key 字段。

### 4.2 密钥选择模式

| 模式 | 常量 | 行为 |
|------|------|------|
| **随机（Random）** | `random` | 每次请求从启用的密钥中随机选一个 |
| **轮询（Polling）** | `polling` | 按顺序依次使用，跳过已禁用的密钥，索引持久化 |
| **默认** | （未设置） | 始终使用第一个启用的密钥 |

### 4.3 轮询模式工作原理

```go
// 从上次保存的索引位置开始
start := channelInfo.MultiKeyPollingIndex
for i := 0; i < len(keys); i++ {
    idx := (start + i) % len(keys)
    if getStatus(idx) == ChannelStatusEnabled {
        // 更新索引指向下一个位置
        channel.ChannelInfo.MultiKeyPollingIndex = (idx + 1) % len(keys)
        return keys[idx], idx, nil
    }
}
```

- **线程安全**：使用 per-channel 的互斥锁 (`GetChannelPollingLock`)
- **索引持久化**：非内存缓存模式下保存到数据库，内存模式下保留在缓存中
- **跳过禁用**：自动跳过被标记为禁用的密钥

### 4.4 密钥状态管理

每个密钥有独立的状态，存储在 `MultiKeyStatusList` map 中：

```go
// map[密钥索引]状态
MultiKeyStatusList map[int]int
// 禁用原因
MultiKeyDisabledReason map[int]string
// 禁用时间
MultiKeyDisabledTime map[int]int64
```

## 5. 密钥自动禁用与恢复

代码位置：`model/channel.go:606-642`, `service/channel.go:21-36`

### 5.1 触发自动禁用的条件

当请求失败时，`ShouldDisableChannel()` 判断是否应该禁用：

| 触发条件 | 说明 |
|---------|------|
| HTTP 401 等状态码 | 由 `ShouldDisableByStatusCode` 配置 |
| HTTP 403 (Gemini) | Gemini 渠道的 403 视为认证失败 |
| `invalid_api_key` | API Key 无效 |
| `account_deactivated` | 账户被停用 |
| `billing_not_active` | 计费未激活 |
| `insufficient_quota` | 额度不足 |
| `authentication_error` | 认证错误 |
| `permission_error` | 权限错误 |
| 自定义关键词匹配 | `AutomaticDisableKeywords` 配置 |

### 5.2 多密钥渠道的禁用逻辑

```
多密钥渠道（10个密钥）
  │
  ├── 密钥#3 报错 invalid_api_key
  │   → 仅禁用密钥#3（MultiKeyStatusList[3] = disabled）
  │   → 渠道整体保持启用
  │
  ├── 密钥#7 报错 insufficient_quota
  │   → 仅禁用密钥#7
  │   → 渠道整体保持启用
  │
  └── 所有 10 个密钥都被禁用
      → 整个渠道自动禁用（Status = AutoDisabled）
      → OtherInfo 记录 "All keys are disabled"
```

**前提**：渠道必须开启了 `AutoBan`（自动禁用）功能。

### 5.3 密钥恢复

管理员可以在渠道管理界面手动恢复被禁用的密钥。恢复操作会从 `MultiKeyStatusList` 中移除对应的索引记录。

## 6. 重试决策逻辑：哪些错误会重试

代码位置：`controller/relay.go:324-354`

### 6.1 一定重试（不消耗重试次数的渠道级错误）

以 `channel:` 为前缀的错误码：
- `channel:no_available_key` — 没有可用密钥
- `channel:invalid_key` — 密钥无效
- `channel:response_time_exceeded` — 响应超时
- `channel:aws_client_error` — AWS 客户端错误
- `channel:param_override_invalid` — 参数覆盖无效
- `channel:model_mapped_error` — 模型映射错误
- `channel:header_override_invalid` — Header 覆盖无效

### 6.2 一定不重试

- 标记了 `skipRetry` 的错误（请求体无效、413 等）
- HTTP 200-299（成功响应）
- Token 绑定了 `specific_channel_id`（指定渠道模式）
- HTTP 504 / 524（超时，由 `AlwaysSkipRetryCode` 控制）
- 剩余重试次数 <= 0

### 6.3 按状态码决定

可配置的 `AutomaticRetryStatusCodes` 控制哪些 HTTP 状态码触发重试。默认会重试的范围：

```
100-199, 300-399, 401-407, 409-499, 500-503, 505-523, 525-599
```

## 7. 渠道亲和性（Channel Affinity）

代码位置：`service/channel_affinity.go`

渠道亲和性让系统记住某个用户/会话之前成功使用的渠道，下次优先使用同一渠道。

### 7.1 工作原理

1. 管理员配置亲和性规则（按模型正则、路径正则等匹配）
2. 首次请求：正常选渠道，成功后将 `(缓存Key → 渠道ID)` 写入缓存（Redis/内存）
3. 后续请求：从缓存取出渠道 ID，直接使用该渠道
4. 缓存有 TTL，过期后重新随机选择

### 7.2 亲和性与重试的关系

如果配置了 `SkipRetryOnFailure = true`：
- 亲和性指定的渠道失败时，**不会重试**，直接返回错误
- 适用于需要强一致性的场景（如同一会话必须打同一个渠道）

## 8. Auto 分组跨组重试

代码位置：`service/channel_select.go:83-162`

当 Token 的分组设为 `auto` 时，系统按配置的分组顺序依次尝试：

```
RetryTimes=5, 分组配置: [GroupA(2个优先级), GroupB(2个优先级), GroupC(1个优先级)]

retry=0: GroupA, priority0 → 失败
retry=1: GroupA, priority1 → 失败
retry=2: GroupA 优先级用完 → GroupB, priority0 → 失败
retry=3: GroupB, priority1 → 失败
retry=4: GroupB 优先级用完 → GroupC, priority0 → 失败
retry=5: GroupC（最低优先级钳制）→ 失败 → 返回错误
```

## 9. 实战场景分析

### 场景一：两渠道不同优先级 + 重试10次

- 渠道 A：10 个密钥，优先级 100
- 渠道 B：5 个密钥，优先级 50
- RetryTimes = 10

| 次数 | retry | 选中优先级 | 选中渠道 | 密钥选择 |
|------|-------|----------|---------|---------|
| 第1次 | 0 | 100 | A | A 的某个密钥 |
| 第2次 | 1 | 50 | B | B 的某个密钥 |
| 第3-11次 | 2-10 | 50（钳制） | B | B 的某个密钥 |

**问题**：只有 2 个优先级梯度，后面 9 次重试全部命中渠道 B。渠道 A 的 10 个密钥只用了 1 个就切走了。

### 场景二：两渠道相同优先级 + 重试10次

- 渠道 A：10 个密钥，优先级 100，权重 10
- 渠道 B：5 个密钥，优先级 100，权重 5
- RetryTimes = 10

| 次数 | retry | 选中优先级 | 选中渠道 | 概率 |
|------|-------|----------|---------|------|
| 第1-11次 | 0-10 | 100（唯一） | A 或 B | A: 2/3, B: 1/3 |

每次重试都在 A、B 之间加权随机。但同一渠道的同一密钥可能被反复选中。

### 场景三：单渠道10密钥 + 轮询模式

- 渠道 A：10 个密钥，轮询模式，优先级 100
- RetryTimes = 10

| 次数 | retry | 选中渠道 | 密钥选择 |
|------|-------|---------|---------|
| 第1次 | 0 | A | key#0 |
| 第2次 | 1 | A（唯一渠道，钳制） | key#1 |
| 第3次 | 2 | A | key#2 |
| ... | ... | A | key#N |
| 第11次 | 10 | A | key#10（若有，否则回到 key#0） |

单渠道场景下，每次重试都会重新选同一渠道，**轮询模式能保证每次使用不同密钥**。

## 10. 多密钥最佳实践：如何用到极致

### 10.1 选择正确的多密钥模式

| 场景 | 推荐模式 | 理由 |
|------|---------|------|
| 密钥有 RPM/TPM 限制，需要均匀分散 | **轮询（Polling）** | 严格按顺序轮流，确保每个密钥均匀使用 |
| 密钥无差别，只需负载均衡 | **随机（Random）** | 简单高效，大样本下近似均匀 |
| 有主备关系，平时只用第一个 | **默认（不设置）** | 始终使用第一个启用的密钥 |

### 10.2 优先使用轮询模式实现密钥均匀利用

轮询模式是让每个密钥都被"照顾到"的最佳选择：

- **严格有序**：key#0 → key#1 → key#2 → ... → key#N → key#0
- **自动跳过禁用密钥**：某个密钥被自动禁用后，轮询会跳过它
- **并发安全**：使用 per-channel 互斥锁保护，不会重复分配
- **索引持久化**：重启后继续上次位置（非内存模式下写入数据库）

### 10.3 单渠道多密钥 + 充足重试次数

如果你有一个渠道配了 10 个密钥，想让重试时覆盖尽可能多的密钥：

```
推荐配置：
- 多密钥模式：轮询（Polling）
- RetryTimes：>= 密钥数量（如 10）
- AutoBan：开启
```

**效果**：
- 请求失败 → 系统重试 → 重新选同一渠道 → 轮询到下一个密钥
- 如果密钥 #3 是坏的（如 invalid_api_key），它会被自动禁用
- 下次轮询自动跳过 #3，使用 #4
- 10 次重试理论上可以遍历所有 10 个密钥

### 10.4 多渠道多密钥 + 优先级策略

如果你有多个渠道，每个渠道配多密钥，想同时利用"跨渠道重试"和"密钥轮换"：

**策略一：拉平优先级（推荐大多数场景）**

```
渠道 A：10 密钥，优先级 100，权重 10，轮询模式
渠道 B：5 密钥，优先级 100，权重 5，轮询模式
RetryTimes = 10
```

- 每次重试都在 A、B 之间加权随机选择
- 选中哪个渠道，就在那个渠道内轮询下一个密钥
- 10 次重试有可能分散在两个渠道的不同密钥上
- 权重控制流量比例：A 获得约 2/3 流量，B 获得约 1/3

**策略二：梯度优先级（主备场景）**

```
渠道 A（主力）：10 密钥，优先级 100，轮询模式
渠道 B（备用）：5 密钥，优先级 50，轮询模式
RetryTimes = 10
```

- 首次请求必定打渠道 A
- 渠道 A 失败 → 第 1 次重试切到渠道 B
- 之后的重试都在渠道 B（因为只有 2 个优先级梯度）
- **缺点**：渠道 A 只用了 1 个密钥就切走了

**策略三：多梯度优先级（精细控制）**

如果想让渠道 A 的密钥被充分利用后再切到渠道 B：

```
方案：将渠道 A 的 10 个密钥拆成多个子渠道
渠道 A-1：密钥 1-3，优先级 100
渠道 A-2：密钥 4-6，优先级 90
渠道 A-3：密钥 7-10，优先级 80
渠道 B：5 密钥，优先级 50
RetryTimes = 10
```

- retry=0 打 A-1（优先级 100）
- retry=1 打 A-2（优先级 90）
- retry=2 打 A-3（优先级 80）
- retry=3+ 打 B（优先级 50）
- 这样渠道 A 的密钥能在前 3 次重试中被逐步覆盖

### 10.5 开启 AutoBan 实现密钥级自动摘除

```
推荐：所有多密钥渠道都开启 AutoBan
```

效果：
- 某个密钥报 `invalid_api_key` → 仅禁用该密钥，不影响其他密钥
- 某个密钥报 `insufficient_quota` → 仅禁用该密钥
- 所有密钥被禁用 → 整个渠道自动下线
- 管理员会收到通知邮件

### 10.6 设定合理的重试次数

| 配置 | 推荐 RetryTimes |
|------|----------------|
| 单渠道 N 个密钥 | N 或 N-1 |
| M 个渠道 M 个优先级 | M 或 M+几 |
| 同优先级多渠道 | 3-5（再多也可能选到同一个） |
| 混合场景 | 优先级梯度数 + 最大渠道密钥数 |

**注意**：重试次数过大会导致用户等待时间过长。建议根据实际 P99 响应时间权衡。

### 10.7 配置总结速查表

| 目标 | 多密钥模式 | 优先级策略 | RetryTimes | AutoBan |
|------|-----------|-----------|------------|---------|
| 每个密钥都用到 | 轮询 | 同优先级 | >= 密钥数 | 开启 |
| 负载均衡 | 随机/轮询 | 同优先级 + 按权重 | 3-5 | 开启 |
| 主备切换 | 轮询 | 不同优先级 | >= 优先级梯度数 | 开启 |
| 极致覆盖 | 轮询 | 拆子渠道多梯度 | >= 子渠道数 | 开启 |
| 最大化利用所有密钥 | 轮询 | 所有渠道同优先级 | 10+ | 开启 |
