# 额度预警阈值 / 等价金额 功能实现梳理

本文梳理个人设置里这段文案对应的完整实现：

> 额度预警阈值（等价金额）  
> 当剩余额度低于此数值时，系统将通过选择的方式发送通知

---

## 1. 功能目标

用户可在个人设置中配置：

- 预警阈值（`quota_warning_threshold`）
- 通知方式（`notify_type`：email/webhook/bark/gotify）
- 对应通知通道参数（邮箱、Webhook 地址、Bark URL、Gotify URL/Token/Priority）

当请求扣费后，若“剩余额度 < 阈值”，系统会异步发送额度预警通知（带限频）。

---

## 2. 前端入口与字段

前端界面在：

- `web/src/components/settings/personal/cards/NotificationSettings.jsx`

核心字段：

- `warningType`（通知方式）
- `warningThreshold`（额度预警阈值）
- `notificationEmail` / `webhookUrl` / `webhookSecret` / `barkUrl` / `gotifyUrl` / `gotifyToken` / `gotifyPriority`

保存接口：

- `PUT /api/user/setting`

由 `web/src/components/settings/PersonalSetting.jsx` 组装请求体，字段映射为：

- `notify_type`
- `quota_warning_threshold`
- 以及各通知通道参数

---

## 3. “等价金额”是怎么显示的

### 3.1 UI 文案来源

`NotificationSettings.jsx` 的阈值标题会调用：

- `renderQuotaWithPrompt(notificationSettings.warningThreshold)`

实现位于：

- `web/src/helpers/render.jsx`

逻辑：

- 若 `quota_display_type !== 'TOKENS'`，显示 `等价金额：` + `renderQuota(...)`
- 若显示模式是 `TOKENS`，则不显示“等价金额”提示

### 3.2 换算公式

`renderQuota(quota)` 的核心换算：

1. 从本地取 `quota_per_unit`
2. `resultUSD = quota / quota_per_unit`
3. 再根据展示币种做转换：
   - `USD`：直接 `$resultUSD`
   - `CNY`：乘 `usd_exchange_rate`
   - `CUSTOM`：乘 `custom_currency_exchange_rate` 且用 `custom_currency_symbol`

后端默认常量：

- `common.QuotaPerUnit = 500 * 1000.0`

即额度值本质是“内部 quota 单位”，前端做“额度 -> 货币”展示换算，因此界面上叫“等价金额”。

---

## 4. 后端保存与校验链路

路由注册：

- `router/api-router.go` -> `selfRoute.PUT("/setting", controller.UpdateUserSetting)`

处理函数：

- `controller/user.go` -> `UpdateUserSetting`

### 4.1 请求校验

主要校验规则：

- `notify_type` 必须是：`email/webhook/bark/gotify`
- `quota_warning_threshold > 0`
- Webhook 模式必须有合法 `webhook_url`
- Email 模式若填写了 `notification_email`，需包含 `@`
- Bark 模式必须 URL 合法且 `http://` 或 `https://`
- Gotify 模式必须有 `gotify_url + gotify_token`，URL 合法，优先级 0~10（否则回退 5）

### 4.2 存储方式

设置被组装为 `dto.UserSetting`，然后：

- `user.SetSetting(settings)`
- `user.Update(false)`

用户设置最终存储在 `users.setting`（JSON 字符串）里。

`dto.UserSetting` 结构定义在：

- `dto/user_settings.go`

---

## 5. 请求执行时如何拿到用户设置

鉴权后用户缓存写入上下文：

- `model/user_cache.go` -> `WriteContext`
- `ContextKeyUserSetting` 被写入 `gin.Context`

生成 relay 上下文时拷贝到 `relayInfo`：

- `relay/common/relay_info.go` -> `info.UserSetting`

后续扣费与通知逻辑都从 `relayInfo.UserSetting` 读取。

---

## 6. 预警触发时机（钱包 / 订阅）

核心在：

- `service/quota.go`

### 6.1 钱包路径

`PostConsumeQuota(..., sendEmail=true)` 中，当发生实际额度变化后：

- 计算 `consumeQuota = quota + preConsumedQuota`
- 判断 `relayInfo.UserQuota - consumeQuota < threshold`
- 满足则发送通知

阈值来源优先级：

1. 用户设置 `userSetting.QuotaWarningThreshold`（非 0）
2. 系统默认 `common.QuotaRemindThreshold`

### 6.2 订阅路径

`checkAndSendSubscriptionQuotaNotify` 中：

- `remaining = SubscriptionAmountTotal - usedAfter`
- 若 `remaining < threshold` 则发送通知

即订阅和钱包都走同一套“用户阈值优先、系统阈值兜底”策略。

---

## 7. 通知发送机制

统一入口：

- `service/user_notify.go` -> `NotifyUser`

分发逻辑：

- `email`：优先 `userSetting.NotificationEmail`，为空则回退用户账号邮箱
- `webhook`：调用 `SendWebhookNotify`
- `bark`：调用 `sendBarkNotify`
- `gotify`：调用 `sendGotifyNotify`

消息类型：

- `dto.NotifyTypeQuotaExceed`（值：`quota_exceed`）

内容模板会按通知类型稍有差异（HTML/纯文本），并替换 `{{value}}` 占位符。

---

## 8. 频控与防刷

通知发送前会检查限频：

- `service/notify-limit.go` -> `CheckNotificationLimit(userId, notifyType)`

支持两种存储：

- Redis（启用 Redis 时）
- 进程内 `sync.Map`（未启用 Redis 时）

窗口和次数：

- `NOTIFY_LIMIT_COUNT`（默认 2）
- `NOTIFICATION_LIMIT_DURATION_MINUTE`（默认 10 分钟）

等价于：同一用户 + 同一通知类型，在一个时间窗口内最多发送 N 次。

---

## 9. 系统级默认阈值（与个人阈值关系）

系统设置项：

- `QuotaRemindThreshold`

加载与更新在：

- `model/option.go`（OptionMap 初始化与 `updateOptionMap` 分支）

关系说明：

- 用户设置了 `quota_warning_threshold`（非 0） -> 使用用户值
- 否则 -> 使用系统 `QuotaRemindThreshold`

---

## 10. 关键注意点

1. 这里“阈值”是内部 quota 单位，不是直接美元数值；“等价金额”是前端换算展示。
2. `UpdateUserSetting` 要求阈值 `> 0`，因此无法保存 `0`（禁用）阈值。
3. 通知发送是异步 `gopool.Go(...)`，不会阻塞主请求返回。
4. 通知被限频时会被跳过，不代表阈值判断没触发。
5. Email 模式若通知邮箱为空，会回落到用户账号邮箱；若两者都空则直接跳过发送。

---

## 11. 一条完整链路（时序）

1. 用户在个人设置填写阈值和通知方式并保存  
2. 前端调用 `PUT /api/user/setting`  
3. 后端校验并写入 `users.setting` JSON  
4. 用户发起模型请求，鉴权后将用户设置写入上下文  
5. 请求完成扣费后进入 `PostConsumeQuota`  
6. 若剩余额度低于阈值，异步调用 `NotifyUser`  
7. `NotifyUser` 做限频检查，通过后按 `notify_type` 发送  
8. 用户收到 Email/Webhook/Bark/Gotify 预警

---

## 12. 常见排查建议

### 12.1 “低于阈值但没通知”

优先检查：

- 是否命中限频（10 分钟内次数已满）
- `notify_type` 对应参数是否完整（如 gotify token）
- Email 模式是否存在可用邮箱
- 是否是非扣费请求（quota 变化为 0 时不会触发）

### 12.2 “等价金额显示不对”

优先检查：

- `localStorage.quota_per_unit` 是否正确
- `quota_display_type` 是否为 `USD/CNY/CUSTOM/TOKENS`
- `status` 中汇率字段（`usd_exchange_rate` 或 custom 汇率）是否正确

## 13. 如何配置（实战示例）

### 13.1 通用说明

- 接口路径：`PUT /api/user/setting`
- 鉴权方式：与其他用户自服务接口一致（需要登录态 / Token）
- 请求体字段（当前功能相关）：

```json
{
  "notify_type": "email | webhook | bark | gotify",
  "quota_warning_threshold": 500000,
  "notification_email": "user@example.com",
  "webhook_url": "https://example.com/webhook",
  "webhook_secret": "secret-token",
  "bark_url": "https://api.day.app/yourkey/{{title}}/{{content}}",
  "gotify_url": "https://gotify.example.com",
  "gotify_token": "your-gotify-token",
  "gotify_priority": 5,
  "accept_unset_model_ratio_model": false,
  "record_ip_log": true
}
```

> 其中 `accept_unset_model_ratio_model` / `record_ip_log` 与额度预警无直接关系，但前端会一并提交。

---

### 13.2 Email 模式配置示例

#### 13.2.1 请求示例

```http
PUT /api/user/setting HTTP/1.1
Content-Type: application/json
Authorization: Bearer <your-access-token>

{
  "notify_type": "email",
  "quota_warning_threshold": 500000,
  "notification_email": "alerts@example.com",
  "accept_unset_model_ratio_model": false,
  "record_ip_log": true
}
```

- 阈值含义：当钱包或订阅剩余额度 `< 500000` 时触发预警
- 500000 会被前端显示为大约 `等价金额：$1`（取决于 `quota_per_unit` 与汇率）

#### 13.2.2 成功响应示例

```json
{
  "success": true,
  "message": "设置已保存",
  "data": null
}
```

（`message` 实际为 i18n 文案，对应 `i18n.MsgSettingSaved`）

#### 13.2.3 触发时的预警邮件内容

- 标题类似：“您的额度即将用尽”
- 内容模板（HTML）大致为：

```text
您的额度即将用尽，当前剩余额度为 {{value}}，为了不影响您的使用，请及时充值。
充值链接：<a href='{{value}}'>{{value}}</a>
```

占位符会被替换为：

- 第一个 `{{value}}`：提示文案本身
- 第二个 `{{value}}`：格式化后的剩余额度，例如 `$0.99`
- 第三和第四个 `{{value}}`：充值页面链接

### 13.3 Webhook 模式配置示例

字段要求：

#### 13.3.2 成功响应示例

```json
{
  "success": true,
  "message": "设置已保存",
  "data": null
}
```

#### 13.3.3 触发时的 Webhook 请求示例

请求方式：

- `POST <webhook_url>`
- Header：
  - `Content-Type: application/json`
  - `Authorization: Bearer <webhook_secret>`

请求体示例：

```json
{
  "type": "quota_exceed",
  "title": "额度预警通知",
  "content": "您的额度即将用尽，当前剩余额度为 {{value}}，为了不影响您的使用，请及时充值。<br/>充值链接：<a href='{{value}}'>{{value}}</a>",
  "values": [
    "您的额度即将用尽",
    "$0.99",
    "https://your-server/console/topup",
    "https://your-server/console/topup"
  ],
  "timestamp": 1739950503
}
```

在落地服务侧，可以简单处理为：

```pseudo
if body.type == "quota_exceed":
    # 读取 title / content / values 做告警聚合或转发
```

## 14. 本地自测流程建议

### 14.1 基本验证步骤

1. 登录前端控制台，进入“个人设置 -> 其他设置 -> 通知配置”  
2. 选择一种通知方式（建议从 Email 或 Webhook 开始）  
3. 设置一个较大的阈值，确保当前余额很快会低于它（例如当前余额约 2 美金，可以将阈值设置为等价 1.8 美金的 quota）  
4. 保存设置，确认接口 `PUT /api/user/setting` 返回成功  
5. 在操练场或通过 Token 调用模型多次，直到余额接近并低于阈值  
6. 观察是否收到对应通知（或在 Webhook/Bark/Gotify 侧查看请求日志）

### 14.2 Webhook 本地调试建议

- 可使用 `ngrok` / `frp` 等将本地 HTTP 服务暴露成公网 HTTPS 地址，然后将该地址配置为 `webhook_url`
- 本地简单打印请求体即可观测所有字段：

```bash
curl -X POST https://your-ngrok-domain/webhook -d '{"test": 1}'
```

确认后再接入你内部的告警系统（如飞书/钉钉/Slack 等）。

### 14.3 限频验证

- 将阈值设置在当前余额附近，连续多次触发消耗  
- 预期：前几次会收到通知，当达到 `NOTIFY_LIMIT_COUNT` 后，在同一时间窗口内不再收到新通知  
- 可同时在后端日志中看到 “notification limit exceeded” 字样，说明是被频控拦截，而不是逻辑没触发。
