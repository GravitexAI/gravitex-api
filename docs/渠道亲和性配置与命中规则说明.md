# 渠道亲和性配置与命中规则说明

本文档说明项目中“渠道亲和性”功能的配置结构、命中条件、前后端展示条件，以及后端代码如何使用该功能。

## 1. 功能目标

渠道亲和性的目标是让“同一类请求”尽量稳定命中同一个渠道，减少渠道切换带来的行为差异。

典型场景：

- 同一个用户持续使用同一个渠道
- 同一个 token 持续使用同一个渠道
- CLI 客户端按固定会话键持续使用同一个渠道
- 指定模型族在指定分组下持续使用同一个渠道

## 2. 配置结构

后端配置结构定义在 [setting/operation_setting/channel_affinity_setting.go](/Users/kocdehub/workspace/gocode/gravitex-api/setting/operation_setting/channel_affinity_setting.go:5)。

顶层结构：

```json
{
  "enabled": true,
  "switch_on_success": true,
  "keep_on_channel_disabled": false,
  "max_entries": 100000,
  "default_ttl_seconds": 3600,
  "rules": []
}
```

单条规则结构：

```json
{
  "name": "qwen user affinity",
  "model_regex": ["^qwen-.*$"],
  "path_regex": ["/v1/chat/completions"],
  "user_agent_include": [],
  "key_sources": [
    { "type": "context_int", "key": "id" },
    { "type": "context_int", "key": "token_id" }
  ],
  "value_regex": "",
  "ttl_seconds": 3600,
  "param_override_template": {},
  "skip_retry_on_failure": false,
  "include_using_group": true,
  "include_model_name": false,
  "include_rule_name": true
}
```

## 3. 顶层配置项说明

### `enabled`

是否启用渠道亲和性。

- `true`：启用
- `false`：完全关闭

### `switch_on_success`

请求成功后，是否将“最终成功的渠道”写回亲和性缓存。

- `true`：用成功渠道更新缓存
- `false`：用本次原始选中的渠道更新缓存

写回逻辑见 [service/channel_affinity.go](/Users/kocdehub/workspace/gocode/gravitex-api/service/channel_affinity.go:713)。

### `keep_on_channel_disabled`

当缓存命中的渠道当前不可用时，是否保留这条亲和性缓存。

- `false`：不可用就清理缓存
- `true`：不可用也保留缓存，等待后续恢复

清理逻辑见 [middleware/distributor.go](/Users/kocdehub/workspace/gocode/gravitex-api/middleware/distributor.go:133)。

### `max_entries`

缓存最大条目数。用于控制本地热缓存容量。

### `default_ttl_seconds`

默认缓存 TTL，单位秒。

- 规则级 `ttl_seconds > 0` 时优先使用规则值
- 否则回退到这个全局默认值

## 4. 规则字段说明

### `name`

规则名称。

作用：

- 出现在管理端日志 `other.admin_info.channel_affinity.rule_name`
- 参与缓存 key 生成，前提是 `include_rule_name=true`
- 用于管理端按规则名清理缓存

建议：

- 名称可读
- 一个规则名只表达一种请求形态

### `model_regex`

模型名正则，逐行匹配，任意一条命中即可。

示例：

```text
^qwen-.*$
^qwq-.*$
^qvq-.*$
```

### `path_regex`

请求路径正则，逐行匹配，任意一条命中即可。

后端实际匹配的是 `Request.URL.Path`，见 [service/channel_affinity.go](/Users/kocdehub/workspace/gocode/gravitex-api/service/channel_affinity.go:555)。

常见值：

```text
/v1/chat/completions
/v1/responses
/v1/messages
/pg/chat/completions
/v1beta/models/.*
```

建议先从日志中的 `other.request_path` 反查真实路径，再配置。

### `user_agent_include`

按入口请求 `User-Agent` 做包含匹配，忽略大小写。

- 留空：不限制 UA
- 有值：任意一条子串命中即通过

适合：

- Codex CLI
- Claude CLI
- 特定本地客户端

不适合普通通用 API 请求。通用规则建议留空。

### `key_sources`

亲和性 key 来源，按顺序尝试，取到第一个非空值就停止。

后端提取逻辑见 [service/channel_affinity.go](/Users/kocdehub/workspace/gocode/gravitex-api/service/channel_affinity.go:289)。

支持类型：

- `context_int`
- `context_string`
- `request_header`
- `gjson`

#### `context_int`

从 gin context 中读取整数。

适合：

- `id`
- `token_id`
- `specific_channel_id`

#### `context_string`

从 gin context 中读取字符串。

适合：

- `username`
- `group`
- `user_group`
- `token_key`

#### `request_header`

从请求头读取。

适合：

- `X-Tenant-Id`
- `X-User-Id`
- `X-Affinity-Key`

#### `gjson`

从请求 JSON body 读取。

适合：

- `prompt_cache_key`
- `metadata.user_id`

不适合：

- 不稳定、偶发、一次一变的 body 字段

### `value_regex`

对最终取到的 affinity key 再做一层正则校验。

- 留空：不校验
- 有值：key 必须满足正则

适合：

- 只允许数字 ID
- 只允许固定前缀 tenant key

普通情况下建议留空，避免把规则卡死。

### `ttl_seconds`

当前规则的缓存 TTL。

- `0`：使用 `default_ttl_seconds`
- `>0`：使用当前规则的 TTL

### `param_override_template`

命中当前规则后，给最终渠道参数覆盖叠加一段模板。

当前默认主要用于 CLI 场景透传特定 headers，见 [setting/operation_setting/channel_affinity_setting.go](/Users/kocdehub/workspace/gocode/gravitex-api/setting/operation_setting/channel_affinity_setting.go:39)。

普通 OpenAI 兼容客户端一般留空。

### `skip_retry_on_failure`

当请求是“通过亲和性命中渠道”后，如果该请求失败，是否禁止重试到其他渠道。

- `true`：失败后不再切换渠道重试
- `false`：允许按正常重试机制切换渠道

CLI 会话粘性更强时可开启。

### `include_using_group`

是否将 `using_group` 纳入缓存 key。

缓存 key 拼接逻辑见 [service/channel_affinity.go](/Users/kocdehub/workspace/gocode/gravitex-api/service/channel_affinity.go:337)。

建议：

- 大多数场景开启
- 避免不同分组共享同一条亲和性缓存

### `include_model_name`

是否将模型名纳入缓存 key。

建议：

- 同模型族共享同一批渠道时关闭
- 不同模型必须严格隔离渠道时开启

### `include_rule_name`

是否将规则名纳入缓存 key。

建议开启。

原因：

- 便于日志排查
- 便于按规则清缓存
- 避免不同规则互相污染

## 5. 命中规则的充要条件

渠道亲和性要真正“命中并被使用”，必须同时满足下面条件。

### 第一步：规则匹配

在 [service/channel_affinity.go](/Users/kocdehub/workspace/gocode/gravitex-api/service/channel_affinity.go:550) 中按顺序遍历规则。

必须同时满足：

1. `enabled=true`
2. `model_regex` 命中当前模型
3. `path_regex` 命中当前路径，或规则未配置路径
4. `user_agent_include` 命中当前 UA，或规则未配置 UA
5. `key_sources` 中至少一个来源取到了非空 key
6. `value_regex` 留空，或 key 命中 `value_regex`

注意：

- 规则是“按顺序”匹配
- 第一条满足模型、路径、UA、key 的规则就会立即去查缓存
- 即使缓存 miss，也不会继续尝试后面的规则

这是排查时最容易忽略的一点。

### 第二步：缓存命中

规则匹配成功后，会生成缓存 key，并读取缓存：

- 命中：返回偏好 `channel_id`
- 未命中：本次不算“亲和性命中”

相关逻辑见 [service/channel_affinity.go](/Users/kocdehub/workspace/gocode/gravitex-api/service/channel_affinity.go:612)。

### 第三步：缓存命中的渠道当前可用

即使缓存命中了，还必须满足：

- 渠道存在
- 渠道已启用
- 渠道支持当前路径
- 渠道在当前分组下支持当前模型

见 [middleware/distributor.go](/Users/kocdehub/workspace/gocode/gravitex-api/middleware/distributor.go:108)。

### 第四步：真正使用了这个渠道

只有在真正使用了缓存命中的渠道时，才会调用 `MarkChannelAffinityUsed(...)`，把日志字段写进 context，见 [middleware/distributor.go](/Users/kocdehub/workspace/gocode/gravitex-api/middleware/distributor.go:122)。

这意味着：

- 仅仅规则匹配成功，不代表前端会显示渠道亲和性
- 仅仅最终 `channel_id` 相同，也不代表是渠道亲和性导致的

## 6. 首跳与二跳

这是最容易误判的点。

### 首次请求

第一次请求通常流程是：

1. 规则匹配成功
2. 缓存查不到
3. 走普通选路
4. 请求成功后，把本次成功渠道写入缓存

因此：

- 第一次请求通常不会在日志里出现 `channel_affinity`

### 后续请求

同一个 key 的后续请求流程是：

1. 规则匹配成功
2. 缓存命中
3. 渠道可用
4. 写入 `channel_affinity`

因此：

- 第二次、第三次同 key 请求，才更有机会在前端看到渠道亲和性标记

## 9. 推荐配置原则

### 通用原则

1. 规则按请求形态拆开
2. key 尽量稳定
3. 优先使用 context 中已有的用户或 token 标识
4. 普通请求尽量不要依赖 body 中偶发字段
5. 通用规则的 `user_agent_include` 一般留空
6. `include_using_group` 建议开启
7. `include_rule_name` 建议开启

### Key 来源优先级建议

推荐优先顺序：

1. `context_int`
2. `context_string`
3. `request_header`
4. `gjson`

推荐 key：

- `id`
- `token_id`
- `username`
- `group`
- `X-Tenant-Id`

不推荐 key：

- `request_id`
- 随机会话号
- 时间戳
- 每次变化的 body 字段

## 11. 常见排查步骤

### 1. 先查真实请求路径

```sql
SELECT
  JSONExtractString(other, 'request_path') AS request_path,
  count(*) AS cnt
FROM logs
WHERE model_name LIKE 'qwen-%'
GROUP BY request_path
ORDER BY cnt DESC;
```

### 2. 查是否真的有渠道亲和性命中

```sql
SELECT
  id,
  created_at,
  username,
  model_name,
  channel_id,
  request_id,
  JSONExtractString(other, 'request_path') AS request_path,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'rule_name') AS rule_name,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'key_source') AS key_source,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'key_key') AS key_key,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'key_fp') AS key_fp
FROM logs
WHERE JSONExtractString(other, 'admin_info', 'channel_affinity', 'rule_name') != ''
ORDER BY created_at DESC, id DESC
LIMIT 100;
```

### 3. 查指定模型族是否命中

```sql
SELECT
  id,
  created_at,
  username,
  model_name,
  channel_id,
  request_id,
  JSONExtractString(other, 'request_path') AS request_path,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'rule_name') AS rule_name,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'key_source') AS key_source,
  JSONExtractString(other, 'admin_info', 'channel_affinity', 'key_key') AS key_key
FROM logs
WHERE model_name LIKE 'qwen-%'
ORDER BY created_at DESC, id DESC
LIMIT 100;
```

### 4. 重点检查规则顺序

因为后端是“第一条匹配规则即返回”，规则顺序错误会导致：

- 更泛的前置规则先吃掉请求
- 后面更精确的规则永远没机会执行

## 12. 常见误区

### 误区 1：最终 `channel_id` 相同就说明命中了渠道亲和性

错误。

相同 `channel_id` 可能只是普通选路结果相同，不代表是亲和性缓存导致。

### 误区 2：规则匹配成功就会在前端显示

错误。

前端只显示真正“命中并使用了缓存渠道”的请求。

### 误区 3：第一次请求就应该看到亲和性标记

错误。

第一次请求通常是写缓存，后续请求才更容易命中。

### 误区 4：`gjson` 一定比 `context_*` 更好

错误。

`gjson` 非常依赖客户端 body 结构是否稳定。对通用请求，`context_int:id`、`context_int:token_id` 通常更稳。
