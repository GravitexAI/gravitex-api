# 渠道内密钥亲和性设计

## 1. 目标

在保留现有渠道亲和性规则、亲和性 Key 来源和模型适配器接口的前提下，将绑定粒度从“亲和性 Key → 渠道”扩展为“亲和性 Key → 渠道内具体密钥”。功能必须适配普通字符串 API Key、Vertex AI Service Account JSON 以及其他依赖当前渠道密钥的模型类型。

同一个现有亲和性 Key 在 TTL 内应稳定使用同一渠道和同一密钥。绑定密钥不可用时，清理绑定；当前请求优先在原渠道选择其他可用密钥，原渠道没有可用密钥时再切换其他渠道，并在成功后建立新的绑定。

## 2. 非目标

- 不新增用户、Token、会话等亲和性 Key 来源。
- 不把 OAuth access token、Service Account 私钥或普通 API Key 明文写入亲和缓存。
- 不在 OpenAI、Claude、Gemini、Vertex 等适配器中分别实现亲和路由。
- 不改变没有启用渠道亲和性的请求的默认渠道/密钥选择策略。

## 3. 现有流程与改造边界

当前 `Distribute()` 负责渠道亲和命中和普通渠道选择，`SetupContextForSelectedChannel()` 负责为选中渠道选择密钥并写入请求 Context。当前亲和缓存值为 `int` 类型的渠道 ID，而渠道内密钥由 `GetNextEnabledKey()` 按随机或轮询模式选择。

改造应集中在公共渠道选择与亲和服务层：

1. 亲和缓存值改为绑定结构。
2. 亲和命中时返回渠道和指定密钥身份。
3. 公共渠道初始化流程支持指定密钥。
4. 各适配器继续读取 `ContextKeyChannelKey`，无需知道亲和性来源。
5. 重试流程维护当前请求已尝试的渠道/密钥组合。

## 4. 缓存数据结构

```go
type ChannelAffinityBinding struct {
    ChannelID int    `json:"channel_id"`
    KeyIndex  int    `json:"key_index"`
    KeyHash   string `json:"key_hash"`
}
```

缓存 Key 继续沿用现有规则、模型、分组和亲和性值的拼接方式，保持现有 TTL、容量、Redis 命名空间和管理清理能力。

缓存 Value 使用 JSON 编码，兼容 Redis 和本地 HybridCache。读取旧版本整数值时视为旧格式绑定：可以将其作为渠道候选进行一次新的密钥选择，成功后覆盖为新结构；不能假设旧值对应当前渠道的某一个具体密钥。

## 5. 密钥指纹规则

### 5.1 普通字符串密钥

对实际用于上游认证的字符串做规范化后计算 SHA-256。规范化只处理不影响凭证语义的首尾空白，不改变密钥中间内容；多 Key 的分隔和解析沿用现有逻辑。

### 5.2 Vertex Service Account

先解析 JSON，再使用以下稳定字段组成指纹输入：

```text
private_key_id + "\n" + client_email + "\n" + project_id
```

对组合字符串计算 SHA-256。JSON 字段顺序、缩进、换行和空白变化不能导致指纹变化。若缺少 `private_key_id`，仍使用 `client_email + project_id`，并将私钥内容作为必要的后备指纹材料，但绝不持久化原文。

### 5.3 指纹校验

命中时先按 `KeyIndex` 获取当前密钥，再计算指纹：

- 索引存在且 hash 相同：直接使用。
- 索引存在但 hash 不同：遍历当前启用密钥，按 hash 查找。
- 找到匹配密钥：更新绑定中的 `KeyIndex`，保留渠道绑定。
- 找不到匹配密钥：认为密钥已删除或替换，清理绑定并进入恢复流程。

## 6. 选择与恢复流程

### 6.1 初次请求或缓存未命中

沿用普通渠道选择，然后按现有随机/轮询策略选择渠道内密钥。请求成功后保存最终使用的 `ChannelID + KeyIndex + KeyHash`。

### 6.2 渠道和密钥均可用

命中绑定后固定使用指定密钥，并设置现有渠道 Context。Vertex 会继续使用现有的 `channel_id + key_index` access token 缓存键。

### 6.3 密钥不可用

清理当前亲和绑定，并在同一次请求内按以下顺序恢复：

1. 原渠道中选择其他启用密钥，排除当前失败的密钥和本次请求已尝试的密钥。
2. 原渠道没有可用密钥时，清除渠道绑定并使用普通渠道选择逻辑选择其他渠道。
3. 新渠道按其密钥选择策略选取密钥。
4. 请求成功后写入新的绑定。

密钥失败的判断应复用现有渠道错误、自动禁用和多 Key 状态处理，不能只根据 HTTP 状态码猜测凭证是否失效。

## 7. 重试语义

现有 `skip_retry_on_failure` 语义保持不变：只有真正命中渠道和密钥亲和绑定后，规则才可以禁止重试。规则匹配但缓存未命中不能被当作亲和命中。

允许重试时，同一次请求必须记录已尝试的 `(channel_id, key_hash)`，避免回退到刚失败的密钥。重试优先级为：原渠道其他密钥，然后其他满足模型/分组/路径条件的渠道。

## 8. Vertex AI 适配

Vertex Service Account 仍由公共 Context 中的渠道密钥提供给适配器。适配器解析选中的 JSON，使用对应的 `project_id` 构造请求 URL，并用对应的 `client_email/private_key` 换取 token。现有 token 缓存按渠道和密钥索引区分，因此绑定恢复后可直接复用，不需要把 access token 纳入亲和缓存。

Vertex API Key 模式按普通字符串密钥指纹处理。

## 9. 并发与一致性

- 亲和绑定写入采用缓存的原子覆盖语义，最后一次成功请求写入最终使用的绑定。
- 同一亲和 Key 并发首次请求可能产生多个候选密钥；必须保证不会写入明文凭证，最终绑定允许由成功请求覆盖。
- Key 列表发生调整时，以 `KeyHash` 为准修正索引；找不到 hash 时才失效。
- 渠道或密钥禁用后，命中校验不得继续使用旧绑定。
- Redis 可用时继续使用 Redis 作为共享亲和缓存；Redis 不可用时保留现有本地缓存降级行为。

## 10. 日志和管理能力

现有 `other.admin_info.channel_affinity` 保持兼容，并追加非敏感字段：

```json
{
  "channel_id": 123,
  "key_index": 2,
  "key_hash": "前8位或完整指纹"
}
```

不得记录 API Key、Service Account JSON、私钥、JWT 或 OAuth access token。现有按规则清理和全量清理接口继续有效。

## 11. 测试要求

至少覆盖：

1. 普通字符串多 Key 首次写入、后续命中同一 Key。
2. Vertex JSON 字段顺序和换行变化不改变 hash。
3. Key 顺序调整后通过 hash 修正索引。
4. 指定 Key 被禁用后清理绑定并切换同渠道其他 Key。
5. 原渠道无可用 Key 后切换其他渠道。
6. 同一次重试不会重复使用失败的渠道/Key。
7. `skip_retry_on_failure` 仅在真实渠道+密钥命中时生效。
8. Redis 与本地缓存编码均可读写绑定结构。
9. 所有模型适配器仍能从公共 Context 取得正确密钥。
10. 日志只包含密钥索引和指纹，不包含密钥原文。

## 12. 验收标准

- 配置现有亲和规则即可实现用户/Token/会话到渠道内具体密钥的稳定绑定。
- Vertex 多 Service Account 场景下，同一亲和 Key 稳定使用同一 Service Account 和对应 project。
- 密钥变更、禁用、删除和渠道不可用时能够自动恢复。
- 非亲和请求行为不变。
- 现有缓存管理、日志查询和计费链路不因密钥亲和改造而泄露凭证或丢失渠道/密钥信息。

## 13. 当前实现说明

当前实现已将缓存载荷升级为 JSON 字符串，并保留对旧版纯整数渠道 ID 的读取兼容。普通字符串密钥使用首尾空白规范化后的 SHA-256；Vertex Service Account 使用解析后的稳定身份字段生成指纹。新版和旧版管理端日志详情均以追加字段显示密钥索引与指纹，旧日志没有这些字段时继续按旧格式展示。

每条规则新增 `key_affinity_enabled` 开关。字段缺省或为 `false` 时只保留渠道亲和，渠道内 Key 继续按原有策略选择；设为 `true` 后才固定并写入具体 Key 的索引与指纹。默认关闭，便于按规则逐步启用。
