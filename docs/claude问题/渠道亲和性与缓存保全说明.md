# 渠道亲和性与 AWS Claude 缓存保全说明

> 适用场景：多个 AWS Claude 渠道优先级相同、开启轮询，需要避免 Prompt Cache 失效

---

## 一、问题根源：轮询会打散缓存

AWS Claude 的 Prompt Cache（提示词缓存）绑定在**具体的 Bedrock 节点/Key** 上。

当你配置了多个 AWS Claude 渠道（优先级相同），系统默认按轮询方式分发请求：

```
请求1 → 渠道A（缓存建立在 A 上）
请求2 → 渠道B（缓存在 A 上，B 不认识，缓存失效）
请求3 → 渠道A（命中缓存 ✓）
请求4 → 渠道C（缓存失效 ✗）
```

结果：**大量重复传输上下文，缓存命中率极低，成本飙升。**

---

## 二、解决方案：渠道亲和性（Channel Affinity）

渠道亲和性的核心思路：**同一个会话/用户，固定路由到同一个渠道**。

### 工作原理（三步）

```
Step 1：从请求中提取「亲和性 Key」
         ↓
         例如：从请求体中读取 metadata.user_id = "user_123"

Step 2：查缓存，看这个 Key 之前用过哪个渠道
         ↓
         缓存命中 → 直接使用该渠道（跳过轮询）
         缓存未命中 → 走正常轮询选渠道

Step 3：请求成功后，记录「user_123 → 渠道A」到缓存
         ↓
         下次同一个 user_123 的请求，直接走渠道A
```

这样，同一个用户的请求始终落到同一渠道，AWS Claude 的 Prompt Cache 不会因为换渠道而失效。

---

## 三、AWS Claude 内置规则

系统已内置 **Claude CLI Trace** 规则，专门处理 claude-* 模型：

| 配置项 | 值 |
|--------|-----|
| 匹配模型 | `claude-*`（所有 Claude 模型） |
| 匹配路径 | `/v1/messages` |
| 亲和性 Key 来源 | 请求体 `metadata.user_id` 字段 |
| 缓存有效期 | 默认 1 小时（TTL=3600s）|
| 失败是否跳过重试 | 可配置 |

**也就是说：只要客户端在请求时携带 `metadata.user_id`，系统就会自动保证该用户的请求路由到同一渠道。**

### 客户端请求示例

```json
POST /v1/messages
{
  "model": "claude-3-5-sonnet-20241022",
  "metadata": {
    "user_id": "user_123"
  },
  "messages": [...]
}
```

## 四、⚠️ 重要限制：渠道亲和性 与 渠道多 Key 不能同时使用

> 这是使用渠道亲和性保全 Prompt Cache 时**最关键的一条规则**，主人一定要注意呀！

### 限制说明

渠道亲和性的绑定粒度是**渠道 ID（Channel ID）**，**不是渠道内的具体 Key**。

源码对应：
- `service/channel_affinity.go:545` 的 `GetPreferredChannelByAffinity` —— 缓存中存的是 `channelID`（int）
- `model/channel.go:128` 的 `GetNextEnabledKey` —— 渠道内多 Key 按 `Random` / `Polling` 模式独立选择，不受亲和性控制

### 两层选择是独立的

```
┌─────────────────────────────────────────────────────────────┐
│  第一层：渠道选择（受亲和性控制）                            │
│    用户 user_123 → 固定路由到 渠道A                          │
├─────────────────────────────────────────────────────────────┤
│  第二层：渠道内 Key 选择（独立运行，不受亲和性控制）        │
│    渠道A 内有 [Key1, Key2, Key3]                            │
│    每次请求按 Random / Polling 选不同的 Key                 │
└─────────────────────────────────────────────────────────────┘
```

### 实际效果对比

| 场景 | 渠道选择 | Key 选择 | Prompt Cache 命中 |
|------|---------|---------|------------------|
| 单渠道 + 单 Key | 固定 | 固定 | ✅ 高 |
| **多渠道 + 单 Key/渠道** + 亲和性 | 固定到同一渠道 | 固定（渠道内只有一个） | ✅ 高 |
| **多渠道 + 多 Key/渠道** + 亲和性 | 固定到同一渠道 | ❌ 渠道内仍随机/轮询 | ❌ 还是会失效 |
| 多渠道（无亲和性） | 轮询 | 渠道内再轮询 | ❌ 最低 |

### 原因：AWS Bedrock Prompt Cache 绑定到 Key

AWS Bedrock 的 Prompt Cache 是**绑定到具体 Key（凭证）** 上的：
- 用 Key1 建立的缓存，用 Key2 请求**完全不识别**
- 渠道亲和性只能保证「固定渠道」，不能保证「固定 Key」
- 因此渠道内一旦配了多 Key，Prompt Cache 还是会被打散

### ✅ 正确做法

如果需要 AWS Claude 的 Prompt Cache 保全，必须满足以下**任一**条件：

1. **每个渠道只配置一个 Key**（推荐 ✨）
   - 一个渠道 = 一个 Key
   - 需要多 Key 时，拆成多个独立渠道，统一优先级
   - 配合渠道亲和性 + `metadata.user_id`，即可实现 Key 级别的稳定绑定

2. **关闭渠道内的多 Key 模式**
   - 把 `ChannelInfo.IsMultiKey` 设为 false
   - 多余的 Key 移除或迁移到新渠道

### ❌ 错误做法（会导致缓存失效）

```
❌ 一个 AWS Claude 渠道配置了 5 个 Key（Random / Polling 模式）
   + 开启渠道亲和性
   → 用户固定路由到此渠道，但每次请求渠道内随机选 Key
   → Prompt Cache 仍然失效，亲和性形同虚设
```

### 配置示意

| 配置 | 是否推荐 | 说明 |
|------|---------|------|
| 渠道 A（单 Key）+ 渠道 B（单 Key）+ 亲和性 | ✅ 推荐 | 标准用法 |
| 渠道 A（多 Key 轮询） + 亲和性 | ❌ 不推荐 | Key 级别失效，亲和性无意义 |
| 渠道 A（单 Key）+ 渠道 B（多 Key） | ⚠️ 部分有效 | 落到 A 的请求 OK，落到 B 的请求缓存仍会失效 |

## 五、缓存机制详解

### 缓存 Key 的组成

```
new-api:channel_affinity:v1:[规则名]:[模型名]:[用户分组]:[亲和性值]
```

例如：
```
new-api:channel_affinity:v1:claude-cli-trace:claude-3-5-sonnet:default:user_123
```

### 双层缓存架构

```
请求 → 先查内存LRU缓存（毫秒级）
         ↓ 未命中
       再查 Redis 缓存（毫秒级）
         ↓ 未命中
       走轮询逻辑选渠道
```

- **内存缓存**：热点数据，容量 10 万条，速度最快
- **Redis 缓存**：持久化，多实例共享，默认 TTL 1 小时
- **容灾**：Redis 故障时自动降级到内存缓存

## 六、日志记录

每次请求命中渠道亲和性规则时，日志的 `admin_info` 字段会包含 `channel_affinity` 信息：

```json
{
  "admin_info": {
    "channel_affinity": {
      "reason": "claude-cli-trace",       // 触发的规则名
      "rule_name": "claude-cli-trace",
      "model": "claude-3-5-sonnet",       // 请求的模型
      "request_path": "/v1/messages",     // 请求路径
      "channel_id": 42,                   // 被固定路由到的渠道ID
      "key_source": "gjson",              // 亲和性Key的来源方式
      "key_path": "metadata.user_id",     // 从请求体哪个字段取的Key
      "key_hint": "user_1...23",          // Key的截断展示（防止泄露完整值）
      "key_fp": "a1b2c3d4"               // Key的SHA1指纹（前8字节，用于日志查询）
    }
  }
}
```

### 日志字段说明

| 字段 | 含义 |
|------|------|
| `reason` | 命中的规则名称 |
| `channel_id` | 这次被路由到的渠道 ID |
| `key_hint` | 亲和性 Key 的截断预览，方便排查 |
| `key_fp` | 亲和性 Key 的 SHA1 指纹，可用于查询某用户的历史路由记录 |

## 七、管理接口

### 查看亲和性缓存统计

```
GET /api/channel_affinity_cache
```

### 清空全部亲和性缓存

```
DELETE /api/channel_affinity_cache?all=true
```

### 清空指定规则的缓存

```
DELETE /api/channel_affinity_cache?rule_name=claude-cli-trace
```

### 查询某用户的路由历史（按 key_fp）

```
GET /api/log/channel_affinity_usage_cache?rule_name=claude-cli-trace&key_fp=a1b2c3d4
```

## 八、常见问题

### Q：不携带 metadata.user_id 怎么办？

没有 `user_id` 就无法提取亲和性 Key，请求会走正常轮询，不享受缓存保全。  
建议所有客户端接入时统一在 `metadata.user_id` 中传入稳定的用户标识。

### Q：渠道 A 宕机了，还会路由过去吗？

默认会重试其他渠道。如果配置了 `skip_retry_on_failure=true`，亲和渠道不可用时直接返回失败，不回退到其他渠道（适合对一致性要求极高的场景）。

### Q：缓存过期了怎么办？

TTL 默认 1 小时。过期后下次请求走正常轮询，选到新渠道后重新建立绑定。期间会有一次缓存失效，但之后恢复正常。

### Q：多个规则同时匹配怎么处理？

按规则列表顺序，**第一个匹配的规则生效**，后续规则忽略。

### Q：开启了亲和性，为什么 Prompt Cache 还是没命中？

最常见的原因：**该渠道配置了多个 Key**。

渠道亲和性只能保证「固定渠道」，无法保证「固定 Key」。当渠道开启了多 Key 模式（Random/Polling），每次请求仍会在渠道内选不同的 Key，AWS Bedrock 的 Prompt Cache 因 Key 切换而失效。

排查步骤：
1. 检查目标渠道是否开启了多 Key 模式（`ChannelInfo.IsMultiKey`）
2. 若开启，将多 Key 拆分为多个独立渠道（每个渠道只放一个 Key），并设置相同优先级
3. 客户端继续传 `metadata.user_id`，亲和性会自动绑定到拆分后的具体渠道（即具体 Key）

详见本文第四章「重要限制」。

### Q：渠道亲和性能不能做到 Key 级别绑定？

**目前不支持。** 亲和性的最小绑定粒度是渠道 ID（Channel ID）。如需 Key 级别一致性，必须通过「一渠道一 Key」的方式间接实现。

## 九、总结

| | 不开亲和性（纯轮询） | 开亲和性 |
|--|-------------------|-----------| 
| 缓存命中率 | 低（每次换渠道） | 高（固定渠道） |
| 成本 | 高（反复传上下文） | 低 |
| 渠道容灾 | 自动轮询备用 | 绑定渠道优先，失败可重试 |
| 配置复杂度 | 零配置 | 需客户端传 user_id |

### ✅ 推荐做法（满足以下全部条件，Prompt Cache 才能真正生效）

1. **每个 AWS Claude 渠道只配置一个 Key**（关键！多 Key 模式会让亲和性失效）
2. 多个 AWS Claude 渠道使用**相同优先级**，开启轮询
3. 客户端请求时统一在 `metadata.user_id` 中传入稳定的用户标识
4. 系统内置的 `claude-cli-trace` 规则会自动完成「同一用户固定到同一渠道（即同一 Key）」的绑定

### ❌ 反模式（会导致 Prompt Cache 失效，亲和性形同虚设）

- 一个渠道内塞多个 Key + 开启 Random/Polling 模式
- 不传 `metadata.user_id`，无法提取亲和性 Key
- 多个亲和性规则匹配同一请求时，依赖后续规则（实际只有第一条生效）

**核心一句话：亲和性 + 一渠道一 Key = Prompt Cache 保全；亲和性 + 渠道内多 Key = 仍会失效。**
