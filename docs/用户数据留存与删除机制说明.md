# 用户数据留存与删除机制说明

> 文档状态：基于 2026-09-07 当前代码检查整理。本文描述代码实际行为，不等同于法律隐私政策，也不推断部署环境、数据库备份或第三方供应商的实际留存期限。

## 1. 结论摘要

当前系统不是“完全不留存用户数据”。用户数据会按照业务需要进入以下位置：

1. 主数据库：用户账号、登录会话、令牌、充值/兑换、用户设置、资产索引、异步任务等。
2. 日志数据库或主数据库：请求用量、计费、错误、登录和管理操作日志；日志字段可能包含请求内容摘要、IP、请求 ID、上游请求 ID，以及按配置采集的客户端请求头。
3. 异步任务记录：任务请求参数、任务结果、上游响应/结果 URL、计费上下文和内部任务状态可能被持久化。
4. 本地短期缓存：请求体和通过 URL 下载的文件可能暂存于内存或磁盘，但请求结束时由中间件关闭并清理。
5. 外部供应商：视频、图片、音频和资产库功能会把数据或 URL 发送给配置的上游供应商；上游侧的留存期限不由本项目代码统一控制。

代码中目前没有覆盖所有数据类型的统一“用户注销即全量删除”流程，也没有统一的数据库留存天数配置。删除通常由具体业务接口或管理员日志清理接口触发。

## 1.1 模型 API 调用数据留存说明（客户交付版）

对于用户通过本平台调用模型的场景：

- 平台不保存用户提交给模型的输入内容。
- 平台不保存模型返回给用户的输出内容。
- 平台仅记录模型调用所需的用量信息，用于额度扣减、计费、统计和对账，例如输入 Token、输出 Token、调用次数和消耗额度。
- 用量信息不包含用户的完整对话内容、提示词、模型输出正文或上传文件正文。

因此，平台侧的留存范围是“调用用量与计费统计”，不是用户模型对话内容或模型生成结果。模型服务商自身是否保存请求或响应数据，则以对应服务商的隐私政策和服务条款为准。

## 2. 数据分类与存储位置

| 数据类别 | 代码中的主要载体 | 是否持久化 | 主要内容 | 当前删除/过期机制 |
| --- | --- | --- | --- | --- |
| 账号资料 | `model.User` | 是，主数据库 `users` | 用户名、密码哈希/密码字段、邮箱、OAuth 标识、额度、设置、备注、支付客户号等 | 用户使用软删除字段 `DeletedAt`；本文检查范围内未发现统一全量清除流程 |
| 登录会话 | `model.LoginSession` | 是，主数据库 | SID、用户 ID、登录方式、IP、User-Agent、创建/活跃/过期/撤销时间 | 会话有效期为 30 天；撤销记录另有 `USER_SESSION_REVOKED_RETENTION_DAYS` 配置语义，需结合部署版本确认清理任务 |
| API 令牌 | `model.Token` | 是，主数据库 | 令牌标识、名称、额度和关联用户/分组等 | 由令牌管理接口删除或禁用；未发现统一按用户删除的证据 |
| 请求/用量/计费日志 | `model.Log` | 是，日志数据库或配置的日志存储 | 用户、模型、渠道、Token、额度、Token 数、IP、内容、请求 ID、`other` 等 | 支持管理员按时间戳删除；ClickHouse 可通过 `LOG_SQL_CLICKHOUSE_TTL_DAYS` 设置 TTL；默认值 0 表示不启用 TTL |
| 异步任务 | `model.Task` | 是，主数据库 | 用户、任务 ID、状态、失败原因、`Data`、`PrivateData`、`UpstreamRequestBody`、结果 URL、计费上下文等 | 支持按任务业务接口删除/取消的局部操作；本文检查范围内未发现统一任务保留期限 |
| 用户资产索引 | `model.UserAsset`、`model.UserAssetGroup` | 是，主数据库 `t_user_assets`、`t_user_asset_groups` | 用户 ID、渠道、上游资产/分组 ID、URL、文件名、内容类型、大小、状态、描述等 | 用户或管理员删除资产/分组时删除本地记录；删除分组会先删除本地资产记录，再删除分组记录 |
| 充值/兑换/操作记录 | `model.TopUp`、`model.Redemption`、`model.OperLog` | 是，主数据库 | 交易号、支付方式、额度、兑换码状态、操作人、变更摘要、备注等 | 提供业务管理删除接口；未发现统一按用户注销清理流程 |
| 请求体临时缓存 | `common.BodyStorage` | 否，设计为请求生命周期内 | 原始请求体；大请求可能写入磁盘缓存 | `middleware.BodyStorageCleanup` 在请求完成后调用 `Close`；磁盘实现会 `os.Remove` 临时文件 |
| URL 下载的临时文件 | `types.FileSource` 缓存 | 否，设计为请求生命周期内 | 请求处理所需的图片/视频/音频临时内容 | `service.CleanupFileSources` 在请求完成后关闭缓存 |
| 运行日志与失败兜底文件 | logger、`failed_logs.jsonl` | 是，文件系统 | 服务运行日志；批量日志写入失败时将日志 JSONL 追加到本地文件 | 普通日志文件支持按数量或天数清理；`failed_logs.jsonl` 未见统一自动清理逻辑 |

## 3. 重点持久化内容

### 3.1 用户账号与认证数据

`model.User` 明确持久化用户名、密码字段、邮箱、多个 OAuth 平台标识、额度、用户设置、备注和 Stripe Customer 标识等。`AccessToken` 虽然通过 JSON 标签隐藏，但仍是数据库字段，不能视为“不保存”。

登录会话 `model.LoginSession` 还持久化 IP、User-Agent、登录方式和时间字段。会话过期或撤销不会自动等价于立即物理删除。

### 3.2 请求日志可能包含业务内容

`model.Log` 的 `Content` 和 `Other` 是文本字段，日志生成链路会把请求处理结果、错误信息、响应/用量相关信息和扩展字段写入其中。日志还包含用户 ID、模型、渠道、Token 名称、IP、请求 ID 等关联信息。

当用户设置启用请求头日志时，`model.AppendConfiguredClientRequestHeaders` 会把原始客户端请求头写入日志的 `other.client_request_headers`。因此不应在该功能中配置密码、Authorization、Cookie 等敏感头；代码本身只按用户配置的名称筛选，不保证业务上配置的 header 一定不含秘密。

### 3.3 异步任务可能包含原始请求和上游结果

`model.Task` 包含以下高敏感字段：

- `Data`：任务数据或上游返回结果的 JSON。
- `PrivateData`：内部任务状态、上游任务 ID、结果 URL、插件状态、计费上下文和部分内部密钥/令牌上下文。
- `UpstreamRequestBody`：用于异步轮询和计费的上游请求体快照。

提交异步任务时，`controller/relay.go` 会把 `result.UpstreamBodyBytes` 经过 `common.TruncateBase64Content` 后写入 `Task.UpstreamRequestBody`。这不是“完全不保存请求体”：即使二进制/base64 内容被截断或处理，JSON 参数、模型、时长、分辨率等业务字段仍可能留存。

### 3.4 资产数据同时存在本地索引和上游资产库

本地 `t_user_assets` 主要保存上游资产的映射信息和 URL/文件元数据，不代表二进制内容一定在本地数据库中。但创建、校验和查询资产时，代码会调用 BytePlus/其他配置的上游资产接口，因此图片、视频、音频或人像素材可能由上游资产库继续保存。

删除本地资产记录不会自动证明所有上游副本、CDN 缓存、备份或审核记录都已删除；应以对应供应商的删除接口和供应商政策为准。

## 4. 临时数据的生命周期

请求体由 `common.BodyStorage` 管理：小请求使用内存，大请求在启用磁盘缓存且达到阈值时使用临时文件。磁盘存储的 `Close` 会关闭文件并删除临时路径。

API 路由挂载 `middleware.BodyStorageCleanup`，请求完成后执行：

```text
请求处理结束
  -> common.CleanupBodyStorage(c)
       -> BodyStorage.Close()
       -> 删除磁盘临时文件 / 释放内存计数
  -> service.CleanupFileSources(c)
       -> 关闭 URL 下载文件缓存
```

该机制只覆盖请求生命周期缓存，不覆盖已经写入数据库、日志文件、对象存储或供应商资产库的数据。

## 5. 当前删除与保留机制

### 5.1 数据库记录

当前代码提供的是分散式删除能力：用户、令牌、资产、兑换码、操作日志、任务和日志各自拥有部分删除或禁用接口。不能据此推断“删除用户”会级联清理所有关联表、日志、任务、资产和第三方数据。

需要特别区分：

- GORM `DeletedAt` 软删除只改变查询可见性，不等于物理擦除。
- 会话 `RevokedAt` 表示撤销，不等于删除。
- 资产删除接口通常先删除本地映射，并尝试调用上游删除接口；上游失败、备份和 CDN 留存仍需单独核实。

### 5.2 业务日志

系统提供两类日志清理：

1. `DELETE /api/log/`：经典前端使用的同步按时间戳删除接口。
2. `POST /api/system-task/log-cleanup`：默认前端使用的 root 管理异步清理任务。

日志文件还支持 root 管理员按文件数量或按天数删除，且不会删除当前正在写入的日志文件。

ClickHouse 日志表支持环境变量 `LOG_SQL_CLICKHOUSE_TTL_DAYS`：

- 大于 0：按 `created_at + N DAY DELETE` 设置 TTL。
- 小于 0：按代码归一化为 0。
- 0：不设置 TTL，不能当作自动过期。

### 5.3 失败日志兜底文件

`model/log_buffer.go` 在批量写入失败时会向当前工作目录追加 `failed_logs.jsonl`。该文件可能包含完整日志对象，属于额外的本地留存面；当前检查未发现它与普通日志文件清理共用的自动删除逻辑，部署时必须纳入磁盘权限、备份和清理策略。

## 6. 上游和部署侧边界

本项目代码只能证明网关侧的发送和本地保存行为，不能证明以下内容：

- 上游模型供应商是否训练、缓存或保留请求/响应。
- 对象存储、CDN、消息队列、数据库备份和快照的保留期限。
- Java 管理端、ByteHouse/ClickHouse、Redis 独立实例和外部支付系统的清理策略。
- 生产环境是否启用了日志采集、容器标准输出收集或主机级备份。

因此对外文档应把“代码已验证的网关行为”和“需要向部署方/供应商确认的策略”分开表述，不能仅凭本仓库代码承诺“零留存”或固定删除期限。

## 7. 建议补齐的治理项

如果需要形成正式的数据留存政策，建议后续单独定义并实现：

1. 数据分类分级：账号、认证、请求内容、日志、任务、资产、支付和运维审计分别定义敏感级别。
2. 统一保留期限：为每类数据定义默认期限、例外期限、备份期限和删除证明。
3. 用户删除流程：明确主表、关联表、日志、任务、资产本地索引、对象存储和上游资产的删除顺序及失败补偿。
4. 敏感字段策略：默认禁止记录 Authorization、Cookie、密码、API Key 和原始多媒体内容；请求头日志采用明确 allowlist。
5. 任务数据最小化：评估是否必须保存完整 `Data`/`UpstreamRequestBody`，以及是否可以只保留计费和轮询所需字段。
6. 失败日志治理：为 `failed_logs.jsonl` 增加轮转、权限控制和清理规则。
7. 部署清单：把数据库备份、日志采集、对象存储、CDN、Redis 和供应商留存条款纳入发布/运维确认表。
