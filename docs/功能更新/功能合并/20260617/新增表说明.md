# 官方更新的表结构变更说明

本次官方合并涉及 **1 张新增表** + **3 张已有表的字段/索引变更**，所有变更均带自动迁移，服务启动时自动执行，无需手动跑 SQL。

---

## 一、新增表：`perf_metrics`（模型性能指标表）

**对应功能：** 管理后台「模型性能看板」

### 这张表是干什么的？

系统在每次 AI 请求完成后，把性能数据自动累加到这张表里，按「模型 + 分组 + 小时」为维度聚合。管理后台的模型性能看板读取这张表，展示每个模型的健康状态。

### 表结构

| 字段 | 类型 | 含义 |
|------|------|------|
| `model_name` | varchar(128) | 模型名称 |
| `group` | varchar(64) | 用户分组（同一模型对不同分组单独统计） |
| `bucket_ts` | bigint | 时间桶时间戳，按小时分桶，一行 = 某模型在某小时的汇总 |
| `request_count` | bigint | 总请求数 |
| `success_count` | bigint | 成功请求数（用于算成功率） |
| `total_latency_ms` | bigint | 所有请求总响应时间（用于算平均延迟） |
| `ttft_sum_ms` | bigint | 流式请求首 token 时间累计（Time To First Token） |
| `ttft_count` | bigint | 有首 token 数据的请求数（分母） |
| `output_tokens` | bigint | 总输出 token 数 |
| `generation_ms` | bigint | 生成总耗时（用于算 token/s 速度） |

### 能算出哪些指标？

| 指标 | 算法 |
|------|------|
| 成功率 | `success_count / request_count × 100%` |
| 平均响应时间 | `total_latency_ms / request_count` |
| 平均首 token 延迟 | `ttft_sum_ms / ttft_count` |
| Token 生成速度 | `output_tokens / generation_ms × 1000`（tokens/秒） |

数据按时间桶滚动保留，旧数据定期清理，不会无限增长。

## 二、已有表变更

### 2.1 `subscription_plans`（订阅套餐表）— 新增 4 个字段

**对应功能：** 订阅付费功能扩展（Waffo Pancake、余额购买、分组升级）

| 新增字段 | 类型 | 默认值 | 含义 |
|---------|------|--------|------|
| `allow_balance_pay` | boolean | true（开启） | 该套餐是否允许用户直接用账户余额购买，关闭后只能通过第三方支付 |
| `waffo_pancake_product_id` | varchar(128) | 空 | 对应 Waffo Pancake 支付网关的商品 ID，不配置则该渠道不可用 |
| `upgrade_group` | varchar(256) | 空 | 用户购买此套餐后自动切换到的用户分组，为空则不切换 |
| `stripe_price_id` | varchar(128) | 空 | 对应 Stripe 的价格 ID（已有 Stripe 集成，此次补充字段） |

**举个例子：** 配置一个「企业版套餐」，设置 `upgrade_group = enterprise`，用户购买后自动从 `default` 分组升级到 `enterprise` 分组，享受更高的模型权限。

---

### 2.2 `user_subscriptions`（用户订阅记录表）— 新增 2 个字段

**对应功能：** 订阅升级/退订时的分组回滚

| 新增字段 | 类型 | 默认值 | 含义 |
|---------|------|--------|------|
| `upgrade_group` | varchar(256) | 空 | 该订阅生效后实际切换到的目标分组 |
| `prev_user_group` | varchar(256) | 空 | 订阅前用户所在的分组（用于退订时恢复） |

**为什么需要这两个字段？**

记录「改前」和「改后」的分组，确保退订时能正确还原。比如用户原来在 `vip` 分组，购买企业套餐后升到 `enterprise`，退订时系统查 `prev_user_group` 得知要还原到 `vip`，而不是还原到 `default`。

---

### 2.3 `logs`（调用日志表）— 1 个新增字段 + 1 个字段扩容 + 1 个索引调整

**对应功能：** 上游请求追踪、日志查询性能优化

#### 新增字段

| 新增字段 | 类型 | 含义 |
|---------|------|------|
| `upstream_request_id` | varchar(128) | 上游 API 在响应 Header 里返回的请求 ID，方便和上游平台对账排查问题 |

> **和现有 `request_id` 的区别：** 你们已有的 `request_id` 存的是上游响应体里的 `id` 字段（如 `chatcmpl-xxx`），新增的 `upstream_request_id` 存的是上游响应 Header 里的 ID（部分平台会额外在 Header 里返回 `x-request-id`），两者来源不同，不冲突。

#### 字段扩容

| 字段 | 原类型 | 新类型 | 原因 |
|------|--------|--------|------|
| `request_id` | varchar(64) | varchar(512) | 原来长度不够，部分上游返回的 ID 会被截断 |

#### 索引调整

| 索引名 | 原列顺序 | 新列顺序 | 原因 |
|--------|---------|---------|------|
| `idx_created_at_id` | `(id, created_at)` | `(created_at, id)` | 后台按时间范围查日志是最高频操作，调整顺序后这个索引才能被用到，之前的顺序实际上不生效 |
