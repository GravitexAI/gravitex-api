## 一、官方的审计日志是什么

官方在 #7 `d8cb17744`（Access Token 管理与审计日志）和 #13 `3f8a50cf8`（补全 Token/额度操作记录）里新增了一张独立的审计表 `audit_logs`，配一个单独的查看页面，专门记录敏感操作。

| 分类 `category` | 记录内容 |
|---|---|
| `login` | 登录成功/失败、登录方式 |
| `security` | 2FA / Passkey / OAuth 绑定与解绑、改密码、删号 |
| `access_token` | 面板访问令牌创建、轮换、吊销、使用 |
| `operation` | 渠道增删改、API 令牌操作、额度调整、模型/厂商/定价修改、系统设置修改 |

每条记录包含：`event_id`（唯一）、操作人 `user_id`/`username`、**操作当时的角色快照** `actor_role`、`ip`、`user_agent`、`method`、`route`、HTTP `status`、`success`、`request_id`、`content`，以及 JSON 明细 `other`（变更前后值、目标对象等）。

接口与权限：
- `GET /api/audit`：管理员查看，需要 `audit.read` 权限（`service/authz/resources_audit.go`）
- `GET /api/audit/self`：用户查看自己的记录

官方涉及的文件：

| 层 | 文件 |
|---|---|
| model | `model/audit_log.go`（表结构、`RecordAuditLog`、`GetAuditLogs`、`MigrateAuditLogs`）、`model/audit_other.go`（`AuditOther` / `AuditAdminInfo` / `AuditOperation` 明细结构） |
| controller | `controller/audit.go`（`GetAuditLogs`、`recordManageAudit` 新实现） |
| middleware | `middleware/audit.go`（`AccessTokenAudit` 等） |
| 权限 | `service/authz/resources_audit.go` |
| 前端 | `web/src/features/usage-logs/audit/**`、`web/src/routes/_authenticated/usage-logs/audit.tsx` |

## 二、本次为什么没有合入

1. **和被拒绝的安全/会话体系绑在一起。** 审计在第 2 批 #7–#15 里和 UserSession、AuthFlow、Access Token 管理、Argon2id 密码等一起提交，大量记录点和这些功能共用代码。第 2 批按用户决定整批拒绝（Go 不是用户侧入口，鉴权在 Java），审计跟着被一起拒绝了。
2. **改了 alpha 已有函数的签名。** 官方把 `RecordLoginLog`、`RecordLogWithAdminInfo` 改成了新签名（多了 `actorRole`、`AuditOther`、`*gin.Context`），而且管理类日志（`LogTypeManage`）改为只写 `audit_logs`、**不再写 logs 表**。alpha 的 logs 表管理日志会被 Java 和现有页面读取，直接接入会导致这部分记录消失。
3. **日志库不兼容。** 官方把 `audit_logs` 建在日志库 `LOG_DB`，ClickHouse 下用 `MergeTree` 引擎和 `JSON` 类型。alpha 生产日志库是 ByteHouse（`CnchMergeTree`），后续要迁到 ADB，这两个都没有验证过官方建表语句。
4. **前端只有官方新版界面有。** 查看页面在 `web/src`，alpha 实际使用的 classic 和 web/default 都没有，合进来也看不到。

## 三、alpha 现状（已有的同类能力）

| 能力 | 实现 | 说明 |
|---|---|---|
| 管理操作日志 | `controller/audit.go` 的 `recordManageAudit` / `recordManageAuditFor` → `model.RecordOperationAuditLog` | 21 处调用，写入 logs 表（`type = LogTypeManage`），覆盖渠道、令牌、额度、设置、模型同步等 |
| 登录日志 | `model.RecordLoginLog` | logs 表（`type = LogTypeLogin = 9`） |
| OperLog | `model/oper_log.go`、`controller/oper_log.go`、classic `OperLogConfirmModal` | 模型定价、渠道、用户分组变更的确认记录，推送给 Java（清单 7.5） |

缺的是：**独立存储 + 统一结构化明细 + 角色快照 + 专门查看页 + 独立权限**。

## 四、后续实施方案

### 4.1 范围

- **要做**：`operation` 分类（管理操作）的独立审计表、查询接口、查看页面、权限控制
- **不做**：`security`、`access_token` 分类（2FA、Passkey、面板令牌都在 Java 侧，Go 不处理）
- **`login` 分类**：Go 侧只有 RuoYi SSO 透传登录，按需评估，默认不做

### 4.2 步骤

1. **建表（主库 MySQL，不放日志库）**
   - 吸收官方 `model/audit_log.go`、`model/audit_other.go` 的表结构和查询函数
   - `MigrateAuditLogs` 改为在主库 `DB` 上 AutoMigrate，避开 ByteHouse / ADB 兼容问题。审计数据量远小于消费日志，放主库没有压力
   - `other` 列用 `TEXT` 兜底（AGENTS.md：JSON 列需要提供 TEXT 回退），走 `common.Marshal` / `common.Unmarshal`
   - 按 AGENTS.md 在 SQLite / MySQL / PostgreSQL 上验证新库建表和重复启动幂等
2. **双写，不改 alpha 现有日志**
   - 在 `recordManageAuditFor` 里，保留原来写 logs 表的逻辑，**额外**写一条 `audit_logs`（category = `operation`，补上 `actor_role`、`route`、`method`、`request_id`、`success`）
   - `RecordLoginLog`、`RecordLogWithAdminInfo` 保持 alpha 签名不变，避免影响 Java 读取的 logs 表
3. **查询接口**
   - `GET /api/audit`（管理员）、`GET /api/audit/self`（可选），支持按时间、用户、分类、action、成功/失败、request_id 过滤
   - 权限：沿用 alpha 的 RuoYi 管理员鉴权；如需细分，再引入官方 `audit.read` authz 资源
4. **前端页面**
   - 参考官方 `web/src/features/usage-logs/audit/**`，移植到 **web/default**（技术栈一致，React + TS，改动最小）；classic 按需再做
   - 列表列：时间、操作人、角色、action、目标、结果、IP、request_id；详情弹窗展示 `other` 里的变更前后值
5. **补齐记录点**
   - 对照官方的 `recordManageAudit` 调用清单（渠道 20+ 个 action、`option.update`、`redemption.create`、`subscription.plan_reset`、`model.metadata.sync` 等），补上 alpha 还没有的点
6. **数据保留**
   - 增加按天数清理的定时任务（例如默认保留 180 天，可配置）

### 4.3 与 Java 的关系

- `audit_logs` 是 Go 独有的新表，Java 不读不写，不影响共享表
- 如果 Java 后台也要看审计，可以后续由 Java 直接查这张表，或者扩展现在的 OperLog 推送

### 4.4 验收

- [ ] 三种数据库新建与重复启动都没有多余 DDL
- [ ] 每个管理操作同时出现在 logs 表（原样）和 `audit_logs`
- [ ] 非管理员调用 `/api/audit` 返回 403
- [ ] web/default 审计页能按条件筛选并查看明细
