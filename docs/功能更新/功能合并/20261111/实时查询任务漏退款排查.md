# 视频任务实时查询漏退款排查（2026-11-12）

> 起因：合并官方第 10b 批时看到官方修复「实时查询任务时发现已失败，直接写终态导致后台轮询不再退款」（官方测试 `TestRealtimeFetchRefundsTaskItFindsFailed`）。用户要求专门核查 alpha 是否有同样问题。

## 一、结论

**alpha 有同样的问题**，从 2026-03-15（commit `694668c82`，veo 实时查询）起存在。

触发条件（同时满足）：
1. 任务是**提交时预扣费**的视频任务（`tasks.quota > 0`）。按秒 / 按量计费的视频模型提交时不预扣，不受影响。
2. 客户端调用 `GET /v1/videos/:task_id` 或 `GET /v1/video/generations/:task_id` 查询时，**上游已经失败**，且后台轮询还没来得及处理这个任务。

客户端一般几秒查一次，后台轮询间隔更长，所以「客户端先看到失败」并不少见。

后果：
- 预扣的额度**不退还**（用户余额和令牌额度都没退）。
- 不写「视频任务失败」错误日志（type=5），也不写退款日志（type=4，`Video async task failed ..., refund ...`）。

## 二、原因

| 路径 | 发现上游失败后做什么 |
|---|---|
| 后台轮询 `controller.updateVideoSingleTask` | 以当前状态做 CAS 切到 FAILURE；切换成功且 `quota != 0` 时退还用户额度和令牌额度，写退款日志和失败日志 |
| 实时查询 `relay.tryRealtimeFetch` → `controller.CompleteVideoTaskOnUpstreamSuccess` | **只用 `Updates` 写 status=FAILURE、progress=100%、fail_reason，不退款、不写日志** |

任务被写成 FAILURE 之后，后台轮询的查询 `model.GetAllUnFinishSyncTasks` 只取非 SUCCESS / FAILURE 的任务，这个任务再也不会被轮询到，退款就永远不会发生。

## 三、修复（本分支）

`relay/relay_task.go` `tryRealtimeFetch`：上游返回 FAILURE 且任务当前不是 FAILURE 时，不再调用 `CompleteVideoTaskOnUpstreamSuccessFn`，改为对这一个任务同步执行后台轮询的同一套流程：

```go
service.DispatchPlatformUpdate(ctx, task.Platform,
    map[int][]string{task.ChannelId: {upstreamID}}, map[string]*model.Task{upstreamID: task})
```

- 退款、失败日志、CAS 防重复全部复用轮询逻辑；即使后台轮询同时在处理，也只有一方能切换成功，不会重复退款。
- `updateVideoSingleTask` 会原地更新 task 对象，接口返回的仍是失败后的最新状态。
- 成功（SUCCESS）路径不变：仍走 `CompleteVideoTaskOnUpstreamSuccess`（按秒 / 按量计费、GET 兜底计费）。
- 代价：实时查询发现失败时会再向上游拉一次任务状态。

该修复与合并无关，`main-alpha` 上的代码结构相同，可以单独挑到 `main-alpha` 先上线。

## 四、评估历史影响（只读 SQL，未执行）

```sql
-- ① 主库：2026-03-15 以来失败且有预扣的任务
SELECT task_id, user_id, channel_id, platform, quota, finish_time, LEFT(fail_reason, 100) AS reason
FROM tasks
WHERE status = 'FAILURE' AND quota > 0
  AND finish_time >= UNIX_TIMESTAMP('2026-03-15');

-- ② 日志库：这些任务里有轮询路径写的失败日志的（GET 路径不会写）。
--    把 ① 的 task_id 代入 IN 列表；查 logs 必须带 created_at 范围
SELECT DISTINCT request_id
FROM logs
WHERE type = 5 AND request_id IN (/* ① 的 task_id */)
  AND created_at >= UNIX_TIMESTAMP('2026-03-15');
```

① 中有、② 中没有的任务，大概率就是漏退款的，可疑金额 = 这些任务的 `quota` 之和。
注意：超时清理（`sweepTimedOutTasks`）、取渠道失败的批量置失败等路径也不写这条日志，需要结合 `fail_reason` 排除后再定。
