## 一、视频任务实时查询漏退款 🔴

来源：第 10b 批合并时对照官方修复（官方测试 `TestRealtimeFetchRefundsTaskItFindsFailed`）发现，用户 2026-11-12 要求专门核查。

### 1.1 结论

alpha 有这个问题，从 2026-03-15（commit `694668c82`，veo 实时查询）起存在。

触发条件（同时满足）：
1. 任务是**提交时预扣费**的视频任务（`tasks.quota > 0`）。按秒 / 按量计费的视频模型提交时不预扣，不受影响。
2. 客户端调用 `GET /v1/videos/:task_id` 或 `GET /v1/video/generations/:task_id` 查询时，**上游已经失败**，且后台轮询还没处理到这个任务。

客户端一般几秒查一次，后台轮询间隔更长，「客户端先看到失败」并不少见。

后果：预扣的用户额度和令牌额度**不退还**；也不写「视频任务失败」错误日志（type=5）和退款日志（type=4）。

### 1.2 原因

| 路径 | 发现上游失败后做什么 |
|---|---|
| 后台轮询 `controller.updateVideoSingleTask` | CAS 切到 FAILURE；切换成功且 `quota != 0` 时退还用户额度和令牌额度，写退款日志和失败日志 |
| 实时查询 `relay.tryRealtimeFetch` → `controller.CompleteVideoTaskOnUpstreamSuccess` | **只用 `Updates` 写 status=FAILURE、progress=100%、fail_reason，不退款、不写日志** |

任务被写成 FAILURE 后，后台轮询的 `model.GetAllUnFinishSyncTasks` 只取非 SUCCESS / FAILURE 的任务，这个任务不会再被轮询到，退款永远不会发生。

### 1.3 修复方案（补丁已备好）

补丁 commit：`5369f5e86`（在合并分支上提交后已用 revert 撤回）。合并进 `main-alpha` 后执行：

```bash
git cherry-pick 5369f5e86
```

如有冲突，改动只有一处：`relay/relay_task.go` `tryRealtimeFetch` 中，上游返回 FAILURE 且任务当前不是 FAILURE 时，不再调用 `CompleteVideoTaskOnUpstreamSuccessFn`，改为对这一个任务同步执行后台轮询的同一套流程：

```go
if ti.Status == model.TaskStatusFailure && task.Status != model.TaskStatusFailure {
    upstreamID := task.GetUpstreamTaskID()
    service.DispatchPlatformUpdate(context.Background(), task.Platform,
        map[int][]string{task.ChannelId: {upstreamID}}, map[string]*model.Task{upstreamID: task})
} else if CompleteVideoTaskOnUpstreamSuccessFn != nil && ... {
    // 原有成功路径不变
}
```

- 退款、失败日志、CAS 防重复全部复用轮询逻辑；后台轮询同时处理时只有一方能切换成功，不会重复退款。
- `updateVideoSingleTask` 原地更新 task 对象，接口返回的仍是失败后的最新状态。
- 成功（SUCCESS）路径不变，仍走 `CompleteVideoTaskOnUpstreamSuccess`（按秒 / 按量计费、GET 兜底计费）。
- 代价：实时查询发现失败时会再向上游拉一次任务状态。

### 1.4 验收

relay 包测试在基线上就编译不过，补丁没有自动化测试覆盖，需要在测试环境手动验证：
- [ ] 提交一个预扣型视频任务，让上游失败，在后台轮询处理前用 GET 查询：返回失败状态；用户余额、令牌额度都退回；有一条错误日志和一条退款日志
- [ ] 同一个任务重复 GET 不会重复退款
- [ ] 按秒 / 按量计费的视频任务成功后 GET 查询，计费与修复前一致
