# 官方更新的表结构变更说明（2026-07-02）

本次合并涉及 **4 张新增表** + **1 张已有表新增字段**，所有变更均带自动迁移，服务启动时自动执行，无需手动跑 SQL。

---

## 一、新增表：`casbin_rule`（权限规则表）

**对应功能**：细粒度授权系统（authz Casbin）

### 干什么用？

Casbin 是主流的权限库，用一张表存所有权限规则（"哪个角色对哪个资源可以做什么动作"）。系统启动时把这张表读到内存里做权限判定。

### 表结构

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | bigint | 自增主键 |
| `ptype` | varchar(100) | 规则类型（`p` = 策略行，`g` = 分组行） |
| `v0` | varchar(100) | 主体（角色名） |
| `v1` | varchar(100) | 对象（资源） |
| `v2` | varchar(100) | 动作 |
| `v3` ~ `v5` | varchar(100) | 扩展字段 |

### 生产影响

- 首次启动自动建表并插入默认策略（对应 RoleCommonUser/RoleAdminUser/RoleRootUser）
- 修改角色权限后，`authz.ReloadPolicy()` 会刷新内存缓存
- 集群下由 `authz.StartPolicySync` 周期性同步，无需手动配置

---

## 二、新增表：`authz_role`（角色定义表）

**对应功能**：细粒度授权系统

### 干什么用？

存所有角色的元信息（角色名、显示名、描述、是否内置）。搭配 `casbin_rule` 使用。

### 表结构

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | bigint | 主键 |
| `name` | varchar(64) unique | 角色标识（内部用） |
| `display_name` | varchar(64) | 显示名 |
| `description` | varchar(255) | 描述 |
| `is_builtin` | bool | 是否内置（内置角色不可删） |
| `created_at` | int64 | 创建时间 |
| `updated_at` | int64 | 更新时间 |

---

## 三、新增表：`system_tasks`（系统任务实例表）

**对应功能**：SystemTaskRunner

### 干什么用？

每次系统任务运行（渠道测试、模型更新检测、MJ 轮询、异步任务轮询等）都在这张表插一行记录，用于跨实例锁 + 任务历史查询。

### 表结构

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | bigint | 主键 |
| `task_id` | varchar(64) | 全局唯一 ID（如 `systask_xxxxx`） |
| `type` | varchar(64) | 任务类型（`channel_test`/`model_update`/`midjourney_poll`/`async_task_poll`/`log_cleanup`） |
| `status` | varchar(32) | 状态（`pending`/`running`/`succeeded`/`failed`） |
| `active_key` | varchar(64) unique | 抢锁 key（防同一类任务并发） |
| `payload` | text/json | 任务参数（如 `log_cleanup` 里的 target_timestamp） |
| `state` | text/json | 运行中状态（进度百分比、已处理数） |
| `result` | text/json | 完成后的结果摘要 |
| `error` | text | 失败原因 |
| `locked_by` | varchar(64) | 抢到锁的 runner ID |
| `created_at` / `updated_at` | int64 | 时间戳 |

### 生产影响

- 后台「系统信息 → 系统任务」页面读这张表展示运行历史
- 老的任务运行记录可以通过 `log_cleanup` 系统任务定期清理

---

## 四、新增表：`system_task_locks`（任务类型级锁）

**对应功能**：SystemTaskRunner 跨实例互斥

### 干什么用？

同一类任务同一时间只能有一个 runner 在执行（比如全集群只能有一个节点在跑 `channel_test`）。这张表按 `type` 加唯一约束实现分布式锁。

### 表结构

| 字段 | 类型 | 含义 |
|---|---|---|
| `type` | varchar(64) primary key | 任务类型 |
| `task_id` | varchar(64) | 当前持锁的 task_id |
| `locked_by` | varchar(64) | 当前持锁的 runner ID |
| `locked_until` | int64 | 锁过期时间戳（防死锁） |
| `updated_at` | int64 | 更新时间 |

### 生产影响

- 无需运维干预，系统自动抢锁/续期/释放
- 如果一个 runner 崩溃了，锁会在 `locked_until` 过期后被其它 runner 抢走

## 五、既有表新增字段

### 5.1 `users` 表

无字段增加（`AdminPermissions` 字段是内存映射，`gorm:"-:all"` 不落库），但 `group` 列宽从 varchar(256) 缩到 varchar(64)。

**⚠️ 生产影响**：如果生产环境有用户的 group 名超过 64 字符，会写入失败。**合并回 main-alpha 前请主人确认**生产 users.group 最长的实际字符数（可以跑 `SELECT MAX(LENGTH(`+"`group`"+`)) FROM users;`）。

### 5.2 `channels` 表

无新字段（`AzureModelApiVersions`、`ByteplusAssetAK/SK/Region/ProjectName`、`EnableModerationQuery`、`DisableTaskPollingSleep` 都存在 `other_settings` JSON 里，不改 DDL）。

## 六、Java 后端（Gravitex-API-End）影响

**新增表**：`casbin_rule`、`authz_role`、`system_tasks`、`system_task_locks` 都是 Go 后端独有，Java 后端不需要关心。

**修改字段**：`users.group` 列宽变化，Java 后端如果直接读写这个字段要注意长度检查。

## 七、迁移执行方式

| 类别 | Go 后端 | 说明 |
|---|---|---|
| MySQL/PostgreSQL | 自动 | GORM AutoMigrate 建表 + 加字段 |
| SQLite | 自动 | GORM AutoMigrate（ALTER COLUMN 用 ADD COLUMN 兜底） |
| ByteHouse/ClickHouse | ⚠️ | 我们跳过 AutoMigrate，用手动 DDL。**这次没新增 logs 表字段**，无需操作 |

## 八、回滚说明

如果需要回滚这次合并：

1. 4 张新表 + `users.group` 列宽收窄回 256 都可以通过 SQL 手动回滚
2. 但**建议**：直接在 git 层面回滚，重启服务后 AutoMigrate 会保持新表结构（新表不影响老逻辑）
3. `casbin_rule` / `authz_role` 里的策略数据在回滚后可能残留但不会被读取
