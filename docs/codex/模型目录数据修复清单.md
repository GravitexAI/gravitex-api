# Codex 模型目录 —— 数据修复清单

> 配套代码：`model/model_extension.go`、`service/codex_catalog.go`、`relaykit/dto/codex_catalog.go`
> 生成工具：`scripts/codex/gen_codex_catalog.py`
> 核对时间：2026-09-11

代码已经上线的前提下，**能不能进 Codex 模型目录完全取决于 `t_extension_models` 里的数据**。
这份清单列出当前拦住模型的三类数据问题，按优先级排。

---

## 0. 先说一个字段语义问题（改数据前必须先统一口径）

`t_extension_models.context_window` 当前存的口径**不一致**：

| 模型 | 库里的值 | 实际语义 |
|---|---|---|
| `gpt-6-astra` | 1,050,000 | **总窗口**（最大输入 + 最大输出） |
| `kimi-k2.7-code` | 256,000 | **最大输入** |
| `qwen3-max` | 256,000 | **最大输入** |

OpenAI 官方口径是「400,000 总窗口 = 272,000 最大输入 + 128,000 最大输出」，
而 Codex 模型目录要的 `context_window` 是**最大输入**——这正是官方目录里
`gpt-6-astra` 写 272,000 而不是 1,050,000 的原因。

**本次不动这个字段的语义**：代码里用 `service/codex_catalog.go` 的
`codexOfficialWindows` 覆盖表兜住了 OpenAI 系列，库里的值继续服务
MAAS 前端展示。但这个不一致长期会咬人，建议后续单独排期统一口径。

---

## 1. 🔴 最高优先级：codex 系列漏标 `openai-response`

Codex 自 2026-02 起**只走 Responses API**，`chat/completions` 已被移除。
下列模型的 `io_schema.endpoint_types` 只有 `["openai"]`，没有 `openai-response`，
因此被目录构建逻辑拦掉——而这些恰恰是客户最想用的型号。

| model_id | model_name | 当前 endpoint_types |
|---|---|---|
| 116 | `gpt-5-codex` | `["openai"]` |
| 85 | `gpt-5.1-codex` | `["openai"]` |
| 86 | `gpt-5.1-codex-mini` | `["openai"]` |
| 154 | `gpt-5.2-codex` | `["openai"]` |
| 178 | `gpt-5.3-codex` | `["openai"]` |
| 117 | `gpt-5-pro` | `["openai"]` |
| 182 | `gpt-5.4-pro` | `["openai"]` |

**改之前要先确认**：我们对接的上游渠道是不是真的支持这些型号的 `/v1/responses`。
如果上游只有 `/v1/chat/completions`，那正确做法是**不标** `openai-response`，
让它们继续不进 Codex 目录——标了反而让用户一选就 404。

确认支持后执行（先跑 SELECT 核对影响行数，再跑 UPDATE）：

```sql
-- 1) 先看会改哪些行
SELECT e.model_id, m.model_name, e.io_schema
FROM t_extension_models e JOIN models m ON m.id = e.model_id
WHERE e.model_id IN (116, 85, 86, 154, 178, 117, 182)
  AND JSON_SEARCH(JSON_EXTRACT(e.io_schema, '$.endpoint_types'), 'one', 'openai-response') IS NULL;

-- 2) 确认无误后追加 openai-response（幂等：已存在的不会重复追加）
UPDATE t_extension_models e
SET e.io_schema = JSON_ARRAY_APPEND(e.io_schema, '$.endpoint_types', 'openai-response'),
    e.config_version = e.config_version + 1,
    e.updated_time = UNIX_TIMESTAMP()
WHERE e.model_id IN (116, 85, 86, 154, 178, 117, 182)
  AND JSON_SEARCH(JSON_EXTRACT(e.io_schema, '$.endpoint_types'), 'one', 'openai-response') IS NULL;
```

## 2. 🟡 次高优先级：缺 `context_window`

下列模型已标 `openai-response`、主模式也对，但 `context_window` 是 NULL，
目录构建会跳过它们（宁可缺失也不猜值：猜错会让 Codex 过早压缩上下文或请求超限）。

下面的值**需要你们的人逐条核对后再执行**，来源标注如下：
- `搜索核实` = 已通过 OpenAI 官方文档/模型页确认
- `待核实` = 按同系列推断，必须人工确认

| model_id | model_name | 建议 context_window | 建议 max_output_tokens | 来源 |
|---|---|---|---|---|
| 43 | `gpt-5` | 400000 | 128000 | 搜索核实 |
| 42 | `gpt-5-mini` | 400000 | 128000 | 搜索核实 |
| 44 | `gpt-5-chat` | 400000 | 128000 | 待核实 |
| 83 | `gpt-5.1` | 400000 | 128000 | 待核实 |
| 84 | `gpt-5.1-chat` | 400000 | 128000 | 待核实 |
| 128 | `gpt-5.2` | 400000 | 128000 | 搜索核实 |
| 145 | `gpt-5.2-chat` | 400000 | 128000 | 待核实 |
| 234 | `gpt-5.3-chat` | 400000 | 128000 | 待核实 |
| 200 | `gpt-5.4-mini` | 400000 | 128000 | 搜索核实 |
| 199 | `gpt-5.4-nano` | 400000 | 128000 | 待核实 |
| 37 | `gpt-4.1` | 1047576 | 32768 | 待核实 |
| 39 | `gpt-4.1-mini` | 1047576 | 32768 | 待核实 |
| 40 | `gpt-4o` | 128000 | 16384 | 待核实 |
| 41 | `gpt-4o-mini` | 128000 | 16384 | 待核实 |

> 注意：上表的 `context_window` 填的是**总窗口**（沿用库里现有口径，见第 0 节）。
> Codex 侧会话窗口由代码里的 `codexOfficialWindows` 覆盖表负责，两者不冲突。
> 但 `gpt-5.1`/`gpt-5.2`/`gpt-5.3-chat` 这些不在官方目录里的型号，代码会直接用库里的值，
> 所以如果库里填的是总窗口，Codex 会以为能塞 400k 输入而实际只能塞 272k。
> **建议这批不在官方目录里的 OpenAI 型号，`context_window` 按「最大输入」填 272000。**

模板（逐条确认后再放开）：

```sql
UPDATE t_extension_models
SET context_window = ?, max_output_tokens = ?,
    config_version = config_version + 1, updated_time = UNIX_TIMESTAMP()
WHERE model_id = ? AND (deleted_at IS NULL OR deleted_at = '');
```

## 3. 🟢 不用管：非对话模型的小数值不是脏数据

排查早期一度把这些当成脏数据，**结论是误判**，不要改：

| model_id | model_name | context_window | 主模式 | 说明 |
|---|---|---|---|---|
| 47/48/49 | `imagen-4.0-*` | 480 | image | 提示词长度上限，在图像语境下合理 |
| 316/317 | `grok-imagine-image*` | 1024 | image | 同上 |
| 68/81/230 | `veo-3.1-*` | 1024 | video | 同上 |
| 165 | `gemini-embedding-001` | 3072 | embedding | 向量维度/输入上限 |

代码已经按 `io_schema.primary_mode` 过滤，只有 `chat` / `reasoning` 能进 Codex 目录，
所以这些值不会流到 Codex。**按数值大小过滤是错的，按主模式过滤才对。**

gpt-6-astra                    ctx= 272000 * kimi-k2.7-code       ctx= 256000
qwen3-max                      ctx= 256000   seed-1-8-251228      ctx= 256000
seed-2-0-code-preview-260328   ctx= 256000   seed-2-0-lite-260428 ctx= 256000

不必等全部数据补完。
