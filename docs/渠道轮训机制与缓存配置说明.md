# 渠道轮询机制与缓存配置说明

## 1. Redis 与内存缓存的关系

### 1.1 配置方式

| 环境变量 | 作用 | 默认值 |
|---|---|---|
| `REDIS_CONN_STRING` | Redis 连接字符串 | 空（不启用 Redis） |
| `MEMORY_CACHE_ENABLED` | 手动启用内存缓存 | `false` |
| `SYNC_FREQUENCY` | 缓存同步频率（秒） | `60` |

### 1.2 开启 Redis 会自动开启内存缓存

在 `main.go` 中有以下逻辑：

```go
if common.RedisEnabled {
    // for compatibility with old versions
    common.MemoryCacheEnabled = true
}
```

**结论：开启 Redis 后，`MemoryCacheEnabled` 会被自动设为 `true`，无需手动配置 `MEMORY_CACHE_ENABLED=true`。**

### 1.3 两者的职责区分

| 组件 | 职责 |
|---|---|
| **内存缓存（MemoryCache）** | 在进程内存中维护渠道列表（`group2model2channels`）和渠道详情（`channelsIDM`），用于快速的渠道选择，避免每次请求都查数据库 |
| **Redis** | 用于 Token 缓存、用户缓存、限流计数、渠道亲和性（Channel Affinity）缓存等跨进程/分布式场景 |

### 1.4 不开启时的降级行为

- **不开启 Redis + 不开启内存缓存**：每次请求都直接查询数据库（`GetChannel` 函数），性能较差且无法使用多 Key 轮询（轮询索引无法在内存中保持）
- **只开启内存缓存（不开启 Redis）**：渠道选择走内存缓存（高性能），但 Channel Affinity 等功能降级为进程内 LRU 缓存，不支持多实例共享
- **开启 Redis（自动开启内存缓存）**：最佳模式，渠道选择走内存缓存，分布式功能走 Redis

## 2. 渠道选择机制

### 2.1 整体流程

```
用户请求
  |
  v
Distribute() 中间件 (middleware/distributor.go)
  |
  |--> 1. 解析请求中的 model 名称
  |--> 2. 检查 Token 是否指定了固定渠道（SpecificChannelId）
  |       |-- 是 --> 直接使用该渠道
  |       |-- 否 --> 继续
  |--> 3. 检查渠道亲和性缓存（Channel Affinity）
  |       |-- 命中 --> 使用缓存的渠道
  |       |-- 未命中 --> 继续
  |--> 4. 调用 CacheGetRandomSatisfiedChannel()
  |       |-- 如果 group == "auto" --> 按自动分组逻辑遍历
  |       |-- 否则 --> 直接从指定 group 选择
  |--> 5. 调用 GetRandomSatisfiedChannel(group, model, retry)
  |       |-- MemoryCacheEnabled == true  --> 从内存缓存选择
  |       |-- MemoryCacheEnabled == false --> 从数据库选择 (GetChannel)
  |--> 6. 选中渠道后，调用 GetNextEnabledKey() 获取 API Key
  |       |-- 单 Key 模式 --> 直接返回
  |       |-- 多 Key 随机模式 --> 随机选一个启用的 Key
  |       |-- 多 Key 轮询模式 --> 按索引轮询选择下一个启用的 Key
  |--> 7. 设置请求上下文，转发到上游
  v
请求转发到上游 API
```

### 2.2 渠道选择算法（优先级 + 加权随机）

渠道选择实现在 `model/channel_cache.go` 的 `GetRandomSatisfiedChannel` 函数中。

**步骤：**

1. **按 group + model 查找候选渠道**：从 `group2model2channels[group][model]` 获取所有启用的渠道 ID 列表
2. **按优先级分组**：收集所有不同的优先级值，降序排列
3. **根据 retry 次数选择优先级**：`retry=0` 选最高优先级，`retry=1` 选次高优先级，以此类推
4. **在同优先级内加权随机**：
   - 计算该优先级下所有渠道的权重总和（`sumWeight`）
   - 生成 `[0, totalWeight)` 范围内的随机数
   - 遍历渠道，逐个减去权重，随机数降至 0 以下时选中该渠道
5. **权重平滑处理**：
   - 所有权重为 0 时：每个渠道等效权重 100（均匀分布）
   - 平均权重 < 10 时：乘以 100 倍平滑因子（避免低权重时随机性不足）

**示例：**

```
渠道A: priority=10, weight=3
渠道B: priority=10, weight=1
渠道C: priority=5,  weight=2

retry=0 时：从 priority=10 中选择（A 75% / B 25%）
retry=1 时：从 priority=5 中选择（C 100%）
```

### 2.3 自动分组（Auto Group）

当 Token 的 group 为 `"auto"` 时，系统会按顺序遍历预配置的自动分组列表：

1. 先在第一个分组中尝试所有优先级
2. 当前分组无可用渠道时，切换到下一个分组
3. 支持跨分组重试（`CrossGroupRetry`）

## 3. 多 Key 轮询机制

### 3.1 多 Key 模式

每个渠道支持配置多个 API Key（以换行符分隔），并选择 Key 的分配模式：

| 模式 | 常量 | 行为 |
|---|---|---|
| 随机（Random） | `MultiKeyModeRandom` | 从所有启用的 Key 中随机选一个 |
| 轮询（Polling） | `MultiKeyModePolling` | 按索引顺序依次选择下一个启用的 Key |

### 3.2 轮询实现细节

实现在 `model/channel.go` 的 `GetNextEnabledKey` 函数中：

```go
// 1. 获取渠道级别的互斥锁（每个渠道独立锁，不影响其他渠道）
lock := GetChannelPollingLock(channel.Id)
lock.Lock()
defer lock.Unlock()

// 2. 从缓存获取当前轮询索引
start := channelInfo.MultiKeyPollingIndex

// 3. 从 start 位置开始，跳过禁用的 Key，找到下一个启用的 Key
for i := 0; i < len(keys); i++ {
    idx := (start + i) % len(keys)
    if getStatus(idx) == Enabled {
        // 更新索引指向下一个位置
        channel.ChannelInfo.MultiKeyPollingIndex = (idx + 1) % len(keys)
        return keys[idx]
    }
}
```

**关键点：**

- **线程安全**：每个渠道有独立的 `sync.Mutex`（存储在 `sync.Map` 中），保证并发请求下轮询索引的原子性
- **索引持久化**：
  - **内存缓存启用时**：轮询索引保存在内存中的 `channelsIDM` 里，缓存刷新时会保留旧的轮询索引（见 `InitChannelCache` 中的逻辑）
  - **内存缓存未启用时**：每次轮询后调用 `SaveChannelInfo()` 将索引写入数据库，**性能较差**
- **自动跳过禁用 Key**：轮询时只选择状态为 `Enabled` 的 Key，禁用的 Key 会被跳过
- **所有 Key 禁用时**：整个渠道会被标记为自动禁用（`ChannelStatusAutoDisabled`）

### 3.3 Key 状态管理

每个 Key 有独立的状态：

| 状态 | 含义 |
|---|---|
| `Enabled (1)` | 正常可用 |
| `ManuallyDisabled (2)` | 手动禁用 |
| `AutoDisabled (3)` | 自动禁用（请求失败触发） |

状态信息存储在 `ChannelInfo` JSON 字段中：
- `MultiKeyStatusList`：Key 索引 -> 状态
- `MultiKeyDisabledReason`：Key 索引 -> 禁用原因
- `MultiKeyDisabledTime`：Key 索引 -> 禁用时间

### 3.4 为什么轮询必须搭配 Redis 和内存缓存

| 场景 | 轮询行为 | 性能 |
|---|---|---|
| **有内存缓存** | 索引保持在内存中，直接读写，极快 | 高 |
| **无内存缓存** | 每次轮询都要 `SaveChannelInfo()` 写数据库保存索引 | 低 |
| **多实例部署 + 无 Redis** | 各实例内存中的轮询索引独立，无法实现真正的全局轮询 | 不一致 |
| **多实例部署 + 有 Redis** | Redis 开启后自动启用内存缓存；虽然轮询索引仍在各实例内存中，但缓存定期同步可以减少不一致性 | 较好 |

## 4. 渠道亲和性（Channel Affinity）

渠道亲和性是一种"请求粘性"机制，让相同特征的请求（如相同用户、相同对话）尽量路由到同一个渠道，以利用上游的上下文缓存（如 Prompt Cache）。

- **有 Redis**：亲和性缓存存在 Redis 中，支持多实例共享
- **无 Redis**：降级为进程内 LRU 缓存（`HybridCache` 自动切换）

---

## 5. 缓存同步机制

```
启动时
  |
  v
InitChannelCache()  -- 从数据库全量加载渠道到内存
  |
  v
SyncChannelCache(SYNC_FREQUENCY)  -- 后台协程，每 N 秒全量刷新一次
```

- 默认同步频率：60 秒（通过 `SYNC_FREQUENCY` 环境变量配置）
- 同步时会保留多 Key 轮询模式下的轮询索引，避免刷新后索引归零

## 6. 推荐配置

### 生产环境（推荐）

```env
REDIS_CONN_STRING=redis://:password@host:6379/0
REDIS_POOL_SIZE=500
SYNC_FREQUENCY=60
```

开启 Redis 后，`MemoryCacheEnabled` 自动为 `true`，无需额外配置。

### 开发/测试环境（轻量）

```env
MEMORY_CACHE_ENABLED=true
SYNC_FREQUENCY=60
```

不使用 Redis，仅使用进程内内存缓存。轮询功能可用，但不支持多实例。

### 最低配置（不推荐）

不设置 `REDIS_CONN_STRING` 也不设置 `MEMORY_CACHE_ENABLED`：
- 每次请求查数据库选渠道
- 多 Key 轮询每次都写数据库保存索引
- 性能极差，不适合生产使用
