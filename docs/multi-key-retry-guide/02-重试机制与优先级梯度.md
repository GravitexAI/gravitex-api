# 重试机制与优先级梯度

## 重试基本概念

系统设置项 `RetryTimes` 控制最大重试次数（默认 `0` 表示不重试）。设为 `N` 时，一次用户请求最多执行 **N+1 次上游调用**（1 次初始 + N 次重试）。

## 重试流程

```
用户请求
  │
  ▼
retry=0: Distribute() 中间件选择初始渠道（最高优先级，加权随机）
  │        → 调用 GetNextEnabledKey() 选密钥
  │
  ├── 成功 → 返回结果
  │
  └── 失败 → shouldRetry() 判断
        │
        ├── 不重试 → processChannelError() → 返回错误
        │
        └── 重试 → processChannelError()（可能禁用密钥）
              │
              ▼
         retry=1: CacheGetRandomSatisfiedChannel(retry=1)
              → 按优先级梯度选渠道
              → 调用 GetNextEnabledKey() 选密钥
              │
              ├── 成功 → 返回结果
              └── 失败 → 继续重试 ...
                    │
                    ▼
              retry=N: 到达上限，返回最后一次错误
```

## 优先级梯度机制（核心）

这是理解重试行为最关键的概念。

### 算法

```go
// 1. 收集所有渠道的唯一优先级值
uniquePriorities = {9, 5, 0}

// 2. 降序排列
sortedUniquePriorities = [9, 5, 0]

// 3. retry 值直接作为索引
targetPriority = sortedUniquePriorities[retry]

// 4. 如果 retry >= 梯度总数，钳制到最后一个
if retry >= len(sortedUniquePriorities) {
    retry = len(sortedUniquePriorities) - 1
}
```

### 核心规则

**一个 retry 值对应一个优先级梯度，一一映射。**

```
retry=0  →  sortedUniquePriorities[0]  →  最高优先级
retry=1  →  sortedUniquePriorities[1]  →  次高优先级
retry=2  →  sortedUniquePriorities[2]  →  第三优先级
...
retry>=梯度数  →  钳制到最低优先级，反复选择
```

### 同优先级内的选择

当同一优先级有多个渠道时，按渠道**权重**做加权随机：

| 权重情况 | 选择行为 |
|---------|---------|
| 所有权重 > 0 | 按权重比例随机 |
| 所有权重 = 0 | 等概率随机（每个渠道有效权重 = 100） |
| 平均权重 < 10 | 权重乘以 100 平滑后随机 |

## 梯度数量决定一切

这是最容易踩的坑。**不管你设了多少次重试，实际有效的重试梯度取决于你有几个不同的优先级值。**

### 示例：2 个梯度 + 10 次重试

```
渠道 A：优先级 9
渠道 B：优先级 9   ← 和 A 同优先级，只算 1 个梯度
渠道 C：优先级 0
RetryTimes = 10

sortedUniquePriorities = [9, 0]  → 只有 2 个梯度
```

| retry | 梯度索引 | 优先级 | 命中渠道 |
|-------|---------|-------|---------|
| 0 | 0 | 9 | A 或 B |
| 1 | 1 | **0** | **C** |
| 2-10 | 钳制到 1 | 0 | C |

**结果**：retry=1 就直接跳到了最低优先级。A 和 B 总共只用了 1 次，剩下 9 次全打到 C。

### 示例：3 个梯度 + 10 次重试

```
渠道 A：优先级 9
渠道 B：优先级 5
渠道 C：优先级 0
RetryTimes = 10

sortedUniquePriorities = [9, 5, 0]  → 3 个梯度
```

| retry | 梯度索引 | 优先级 | 命中渠道 |
|-------|---------|-------|---------|
| 0 | 0 | 9 | A |
| 1 | 1 | 5 | B |
| 2 | 2 | 0 | C |
| 3-10 | 钳制到 2 | 0 | C |

### 示例：10 个梯度 + 10 次重试

```
渠道 1~9：优先级 9~1（每个不同）
渠道 10：优先级 0
RetryTimes = 10

sortedUniquePriorities = [9,8,7,6,5,4,3,2,1,0]  → 10 个梯度
```

| retry | 优先级 | 命中渠道 |
|-------|-------|---------|
| 0 | 9 | 渠道 1 |
| 1 | 8 | 渠道 2 |
| ... | ... | ... |
| 8 | 1 | 渠道 9 |
| 9 | 0 | 渠道 10 |
| 10 | 0（钳制） | 渠道 10 |

**每个渠道都被用到了。**

## 关键结论

| 要点 | 说明 |
|------|------|
| 优先级数值大小不重要 | 只看有几个**不同**的值。优先级 999 和 1 是 2 个梯度，优先级 9 和 1 也是 2 个梯度 |
| 同优先级的渠道共享一个梯度 | 不管同优先级有多少渠道，retry 只分配 1 次给这个梯度 |
| 重试不会在同优先级内多次尝试 | retry=0 选了优先级 9，retry=1 就必然跳到下一个梯度 |
| 梯度用完后钳制在最低 | 剩余重试次数全部打到最低优先级的渠道 |

## 哪些错误会触发重试

### 一定重试（渠道级错误，不消耗重试次数）

- `channel:no_available_key` — 没有可用密钥
- `channel:invalid_key` — 密钥无效
- `channel:response_time_exceeded` — 响应超时
- `channel:aws_client_error` — AWS 客户端错误
- `channel:param_override_invalid` — 参数覆盖无效
- `channel:model_mapped_error` — 模型映射错误

### 一定不重试

- 标记了 `skipRetry` 的错误（请求体无效、HTTP 413 等）
- HTTP 200-299（成功响应）
- Token 绑定了 `specific_channel_id`（指定渠道模式）
- HTTP 504 / 524（超时）
- 剩余重试次数 <= 0

### 按状态码决定

可配置的 `AutomaticRetryStatusCodes` 控制。默认重试的范围：

```
100-199, 300-399, 401-407, 409-499, 500-503, 505-523, 525-599
```
