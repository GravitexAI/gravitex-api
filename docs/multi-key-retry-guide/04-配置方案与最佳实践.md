# 配置方案与最佳实践

## 常见需求与配置方案

### 场景一：纯负载均衡，密钥无差别

> 10 个密钥，每个都一样，只想分散请求。

```
渠道 A：10 密钥，优先级 0，权重 0，轮询模式
RetryTimes = 3~5
AutoBan = 开启
```

效果：
- 每次请求轮询下一个密钥
- 报错重试时继续轮询（取全局索引的下一个）
- 坏 key 自动禁用，后续自动跳过

### 场景二：多渠道负载均衡

> 渠道 A 有 10 个密钥，渠道 B 有 5 个密钥，想分散使用。

```
渠道 A：10 密钥，优先级 9，权重 10，轮询模式
渠道 B：5 密钥，优先级 9，权重 5，轮询模式
RetryTimes = 5
AutoBan = 开启
```

效果：
- 同优先级只有 1 个梯度，所有重试都在 A/B 之间按权重随机
- A 获得约 2/3 流量，B 获得约 1/3
- 选中哪个渠道，就在那个渠道内轮询下一个密钥

### 场景三：保底密钥（核心需求）

> 9 个普通密钥 + 1 个高成本保底密钥。保底密钥绝不出错，但希望尽量不用它。

**方案 A：拆成 2 个渠道（简单，但保底用得多）**

```
渠道 A（主力）：key#0~#8，优先级 9，轮询模式
渠道 B（保底）：key#9，    优先级 0
RetryTimes = 10
AutoBan = 开启
```

| retry | 优先级 | 渠道 |
|-------|-------|------|
| 0 | 9 | A（轮询取 1 个密钥） |
| 1 | **0** | **B（保底）** |
| 2-10 | 0（钳制） | B |

**问题**：只有 2 个梯度，retry=1 就跳到保底了。A 的 9 个密钥只用了 1 个。

**方案 B：拆成多个子渠道（推荐，覆盖更多密钥）**

```
渠道 A1：key#0, key#1, key#2  → 优先级 9，轮询
渠道 A2：key#3, key#4, key#5  → 优先级 8，轮询
渠道 A3：key#6, key#7, key#8  → 优先级 7，轮询
渠道 B ：key#9               → 优先级 0（保底）
RetryTimes = 4
AutoBan = 开启
```

| retry | 优先级 | 渠道 | 密钥覆盖 |
|-------|-------|------|---------|
| 0 | 9 | A1 | key#0/#1/#2 之一 |
| 1 | 8 | A2 | key#3/#4/#5 之一 |
| 2 | 7 | A3 | key#6/#7/#8 之一 |
| 3 | **0** | **B** | **key#9 保底** |
| 4 | 0（钳制） | B | key#9 |

前 3 次重试覆盖了 A 的 3 组密钥，第 4 次才用保底。

**方案 C：极致覆盖（每个密钥一个渠道）**

```
渠道 1 ：key#0  → 优先级 9
渠道 2 ：key#1  → 优先级 8
渠道 3 ：key#2  → 优先级 7
渠道 4 ：key#3  → 优先级 6
渠道 5 ：key#4  → 优先级 5
渠道 6 ：key#5  → 优先级 4
渠道 7 ：key#6  → 优先级 3
渠道 8 ：key#7  → 优先级 2
渠道 9 ：key#8  → 优先级 1
渠道 10：key#9  → 优先级 0（保底）
RetryTimes = 10
AutoBan = 开启
```

| retry | 优先级 | 密钥 |
|-------|-------|------|
| 0 | 9 | key#0 |
| 1 | 8 | key#1 |
| 2 | 7 | key#2 |
| ... | ... | ... |
| 8 | 1 | key#8 |
| 9 | **0** | **key#9 保底** |

**9 个密钥逐个尝试，全部失败后，最后用保底。** 完美但管理成本最高。

### 场景四：多渠道 + 保底

> 渠道 A（10 密钥）、渠道 B（5 密钥）主力，渠道 C（1 密钥）保底。

**错误配置（常见踩坑）**：

```
渠道 A：优先级 9
渠道 B：优先级 9
渠道 C：优先级 0
```

只有 2 个梯度，retry=1 就跳到 C 了。

**正确配置**：

```
渠道 A：优先级 9，权重 10，轮询
渠道 B：优先级 9，权重 5，轮询
渠道 C：优先级 9，权重 1，轮询    ← 全部同优先级
RetryTimes = 10
```

用**权重**而非优先级来控制保底：C 被选中概率约 1/16 ≈ 6.25%，自然成为"几乎不用"的角色。不过这种方式 C 不是严格保底——正常请求也可能随机到它。

**严格保底的正确配置**：

```
渠道 A1：key#0~#4  → 优先级 5，轮询
渠道 A2：key#5~#9  → 优先级 4，轮询
渠道 B1：key#0~#2  → 优先级 3，轮询
渠道 B2：key#3~#4  → 优先级 2，轮询
渠道 C ：key#0     → 优先级 0（保底）
RetryTimes = 5
```

5 个梯度，前 4 次重试覆盖 A 和 B，第 5 次才用 C。

## 配置速查表

| 目标 | 密钥模式 | 优先级策略 | 权重 | RetryTimes | AutoBan |
|------|---------|-----------|------|------------|---------|
| 均匀负载均衡 | 轮询 | 全部同优先级 | 全 0（等概率） | 3-5 | 开启 |
| 按比例分流 | 轮询 | 全部同优先级 | 按比例设置 | 3-5 | 开启 |
| 密钥逐个覆盖 | — | 每个 key 一个渠道，不同优先级 | 0 | >= 密钥数 | 开启 |
| 保底密钥 | — | 拆渠道，保底设最低优先级 | 0 | >= 梯度数 | 开启 |
| 多渠道 + 保底 | 轮询 | 主力同优先级，保底最低 | 主力 > 0 | >= 梯度数 | 开启 |

## 最佳实践总结

### 1. 优先级梯度数 = 你希望的有效重试层数

想让重试有效覆盖 N 层不同的渠道，就需要 N 个不同的优先级值。

### 2. 同优先级渠道用权重区分

同一优先级内的多个渠道通过权重控制流量比例，不影响梯度降级。

### 3. 轮询模式 + AutoBan 是标配

- 轮询确保密钥均匀使用
- AutoBan 确保坏 key 被自动摘除
- 两者配合使用效果最佳

### 4. RetryTimes 设置原则

```
RetryTimes >= 优先级梯度数
```

如果 RetryTimes < 梯度数，低优先级的渠道永远不会被用到。

### 5. 避免设置过大的 RetryTimes

每次重试都是一次完整的上游请求，10 次重试意味着用户可能等待 10 倍的延迟。建议根据上游 API 的平均响应时间权衡：

| 上游平均响应时间 | 建议 RetryTimes |
|---------------|----------------|
| < 1 秒 | 5-10 |
| 1-5 秒 | 3-5 |
| 5-30 秒 | 1-3 |
| > 30 秒（如视频生成） | 0-1 |

### 6. 保底密钥必须单独拆渠道

多密钥机制内没有密钥级优先级。要实现"最后才用某个 key"的效果，唯一的方法是把那个 key 拆成独立渠道，设最低优先级。
