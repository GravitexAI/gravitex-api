# QuotaStream 为什么这么设计 — 人话版

> 不看代码,不背概念,只讲每个组件解决了什么现实问题。
> 建议先看这篇,再看 `README.md` 的技术细节。

---

## 场景比喻:一家 24 小时便利店

假设你开了一家便利店:

- 每卖出一件商品,收银机就打一张**小票**存档 — 这就是 `logs` 表(明细账,一行一笔)
- 老板想在电视屏上看**每小时销售报表** — 这就是 `quota_data` 表(汇总账,一行一小时)

问题来了:**每卖出一件商品的时候,报表怎么更新?**

---

## 最朴素的做法:卖一笔,改一次报表

```
顾客买了瓶可乐 → 打小票 → 立刻去改报表:"这一小时销售额 +3 元"
```

看起来很直接。但是店里高峰期一分钟几十单,问题就来了:

### 问题 1:收银台被"改报表"拖慢了

小票打完,还得排队等着改报表那一栏的锁。顾客在收银台前干等。
👉 **业务主流程不该被统计功能拖累。**

### 问题 2:改到一半停电了,报表数字就错了

小票写好了(明细账保住了),但报表那一栏还没 +3 就断电了。恢复之后,你怎么知道这笔加没加?
👉 **明细账和汇总账不是同一个事务,永远会有窗口不一致。**

### 问题 3:两个收银员同时改同一小时的报表,数字打架

一个 +3,一个 +5,结果只 +3 或 +5(经典的丢失更新)。
👉 **并发累加天然容易出错,业务上账对不上。**

### 问题 4:程序 bug 让某一笔改了两次,报表数字虚高

一旦 += 累加,重复执行就一定虚高。你都没法事后修正,因为你不知道多加了哪一笔。
👉 **累加型更新是不可逆的,一旦出错很难自愈。**

**结论:** 让收银台和报表脱钩。收银就好好收银,报表让另外一套人去算。

---

## 改进 1:异步 + 用队列

```
顾客买可乐 → 打小票(logs 表)→ 把"这一小时销售额有更新"这条消息扔进一个队列
                                        ↓
                        另外雇几个员工,专门盯着队列,慢慢把报表更新过来
```

- **收银员(业务主流程)** — 只管打小票,不管报表,极快
- **专职算账员(消费者)** — 从队列里拿消息,慢慢改报表,即使慢一点也不影响顾客

这个"队列"就是 **Redis Stream `stream:quota_data:v1`**。

**新问题:** 消息队列虽然快,但也可能塞车、丢失、员工偷懒。所以下面还得继续加保障。

---

## 改进 2:不做"累加",做"整小时重算"

一般人想到"更新销售额"就是 `+= 3`。但前面说了,累加一旦出错就没救。

换个思路:**每次收到消息,不看这一笔多少钱,直接把这一小时所有小票再加一遍,把结果整个覆盖到报表上。**

```
消息来了:"14:00~15:00 有更新"
    ↓
算账员:去翻这一小时的所有小票,重新算总和 = 258 元
    ↓
把报表这一格直接改成 258(不是 +3)
```

好处非常大:

- **重复处理不会错** — 同一条消息重复算 3 次,结果还是 258
- **可以随时对账** — 从明细账重新算一次汇总,永远都是对的
- **不需要维护"这一笔加过没加过"的状态** — 反正结果只依赖当前一小时的所有小票

**这就是"整桶重算"思想。"桶"就是一小时的报表格子。**

---

## 改进 3:多人同抢一小时报表,得先排队

上一步说"重算一小时所有小票"。假设两个算账员同时收到两条消息,都是"14:00~15:00 有更新",他们同时去算、同时写报表,还是会打架。

方案很朴素:**加锁**。谁先拿到"14:00~15:00 这一格的钥匙",谁先算。另一个人等。

- 钥匙就是 Redis 里的 **bucket 锁**
- 等的人也不能干等,他知道"待会儿要重算",就在门上贴张纸(**dirty 标志**),表示"你算完了别急着走,再算一遍,因为我这里也有新数据"

**效果:** 同一小时的并发消息,收敛成一次或几次桶重算,不会重复更新报表。

---

## 改进 4:同一条消息可能被多次投递,得有"完成印章"

Redis Stream 有时会重复投递(网络抖动、消费者崩溃、reclaim 机制),同一条消息可能被两个算账员先后处理。

即使有整桶重算兜底,能不能**直接跳过已经算过的消息**?能。

- 算完一条消息,在 Redis 里盖个印章:"event_id=xxx 已完成"(**doneKey**)
- 下次同一条消息又来,先看印章,有印章就直接扔掉

印章有 24 小时保质期(TTL),够抵抗常见的重复投递窗口。

---

## 改进 5:Redis 队列本身也可能丢消息 — 靠"扫描明细账"兜底

假设 Redis 挂了 30 秒,收银员这段时间打的小票没能塞进队列。等 Redis 好了,报表就永远漏了这 30 秒的销售额。

**兜底方案:** 派一个专职**巡查员**,定时去翻**明细账**(logs 表),按小票编号一张一张往后扫。发现某张小票的对应"报表更新消息"没投进队列过,就补投一个。

- 巡查员就是 **Backfill(补偿扫描器)**
- 只在**总店(master 节点)**跑一个,多店铺(多容器)之间用一个共享钥匙(SetNX 锁)确保同一时间只有一个巡查员在工作
- 他扫到哪张小票了,把编号记在小本子上(**Backfill 游标**),下次从这里接着扫

**关键**:巡查员补投的消息,会被"完成印章"挡住已经处理过的,不会重复算。这也是为什么整桶重算 + 印章的组合这么关键 — Backfill 敢重复投递。

---

## 改进 6:算账员突然请假 — 消息卡在半路

算账员从队列拿了一条消息(称为"pending"状态),还没处理完就下班了 / 崩溃了。这条消息就悬在半空,既没算成,也没退回队列。

对应地又派一个**顶班员**,专门盯着"有谁拿了消息但太久没交作业"。

- 顶班员就是 **Reclaimer(回收器)**
- 每隔几秒扫一遍,发现某条消息**空闲超过 30 秒**(参数可调),就把它抢回来自己算
- 每认领一次算一次重试

---

## 关键问题来了:为什么要死信队列?

前面所有机制都很好,但有些消息**就是永远算不好**。举例:

- 消息内容本身是脏数据(字段缺失、格式错乱)
- 明细账那一小时的数据被人误删,重算永远查不到
- 数据库长期不可用,重试了 5 次每次都失败

如果没有死信队列,会发生什么?

- 顶班员反复认领这条坏消息 → 反复失败 → 又变成 pending → 又被认领 → **无限循环**
- 这条消息会堵住队列后面的正常消息,拖累整个系统
- 应用日志被这一条烂消息刷屏,真正的告警看不见

**死信队列 (DLQ) 就是:"这条消息我已经尽力了,救不了,放这儿等人来看。"**

具体来说:

1. 顶班员数着这条消息重试次数 — 超过 5 次(可配),放弃
2. 把这条消息 + 失败原因 + 重试次数,一起丢进**死信队列** `stream:quota_data:dlq:v1`
3. 从主队列里 ACK 掉,不再打扰其他算账员

死信队列有几个特点:

- **没有自动消费者** — 里面的东西没人自动处理,等着人工看
- **保留完整现场** — 原始消息 + 失败原因(`failed_reason`)+ 是谁失败的(`failed_consumer`)+ 试了几次(`retry_count`),排查起来一目了然
- **是一个明确的告警信号** — 生产正常时 `XLEN stream:quota_data:dlq:v1` 应该长期是 0;一旦有值就是异常,该发钉钉/PagerDuty 了

### 那死信队列里的消息怎么处理?

**看根因,不看数字。**

- 数据被误删?先修数据,再手动补一条 event 让 Backfill 或人工触发重算
- Redis / DB 一直挂?等基础设施恢复,Backfill 会自动扫过来补(死信队列里可以清掉)
- 应用版本不一致产生的脏消息?升级完统一版本,清理死信队列即可
- 就是想强行补一下?可以按里面的 `log_id`/`request_id` 定位到 logs 表那一行,手动触发桶重算

**大部分情况下,人不需要真去"回放"死信消息** — 因为 logs 表这个 Source of Truth 一直在,只要修好根因,Backfill 扫过去时自然会重新走一遍完整流程,quota_data 最终会对上。

**死信队列的核心价值不是"存起来待处理",而是"给我一个明确信号,提醒我这里出问题了"。**

## 一图总结

```
   ┌─────────────────────────────────────────────────┐
   │  收银台(业务主流程)                            │
   │  只做:打小票 → 扔个"这单更新了"的消息进队列    │
   └────────────────────┬────────────────────────────┘
                        │
                        ▼
             ╔════════════════════╗
             ║  队列 (Stream)     ║
             ╚═════════╦══════════╝
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
   算账员 1        算账员 2        算账员 N
   (每人拿一条消息)
       │
       ├─看印章:已算过 → 扔掉
       ├─没算过:抢桶锁 → 整桶重算 → 覆盖报表 → 盖印章 → 交作业
       └─中途出问题:消息悬空(pending)
                       │
                       ▼
               ┌──────────────┐
               │  顶班员      │  发现 30 秒没交作业的消息
               │ (Reclaimer)  │  抢过来自己算
               └──────┬───────┘
                      │
                      ▼
                重试超过 5 次
                      │
                      ▼
             ┌─────────────────┐
             │  死信队列 DLQ   │  ← 人工看这里,处理疑难杂症
             └─────────────────┘

   另外还有:
   ┌──────────────────────────────────────────────┐
   │  巡查员(Backfill,总店独一份)               │
   │  定期翻明细账,发现漏投消息就补投            │
   │  → 靠印章防止重复算                          │
   └──────────────────────────────────────────────┘
```

## 一句话总结每个组件

| 组件 | 一句话解释 |
|---|---|
| logs 表 | 明细账,永远相信它 |
| quota_data 表 | 汇总账,靠算账员从明细账算出来 |
| Stream 主队列 | 通知算账员"这一小时有活了" |
| 算账员 (Consumer) | 拿到消息就整小时重算,不做累加 |
| 桶锁 + dirty | 同一小时的多个消息串行处理,不打架 |
| 完成印章 (doneKey) | 短期内已算过的消息直接跳过,防重复 |
| 顶班员 (Reclaimer) | 消息卡在算账员手里太久就抢过来 |
| 巡查员 (Backfill) | 兜底扫明细账,防 Redis 抖动漏消息 |
| **死信队列 (DLQ)** | **告诉运维:这里有救不了的消息,该人工看看了** |

## 常见困惑答疑

### Q1:为什么不直接每次 update += ?

**A:** 累加语义不可逆,一旦出错(重复执行、进程崩溃、并发冲突)永远修不回来。整小时重算的语义是"结果 = 当前一小时所有明细的 SUM",无论重算多少次都对。

### Q2:为什么不同步落库,而要走 Stream?

**A:** 三个原因:
1. **性能** — 业务主流程不该等报表更新
2. **削峰** — 高峰期收银很快,算账员慢一点也不影响顾客
3. **解耦** — 报表逻辑改坏了不影响收银

### Q3:为什么已经有 Backfill 了,还要 Reclaimer?

**A:** 分工不同:
- **Backfill** 兜底"消息根本没进队列"(Producer 端漏投)
- **Reclaimer** 兜底"消息进了队列但没算完"(Consumer 端卡壳)

两个方向都要覆盖才能达到最终一致。

### Q4:为什么整桶重算不会很慢?

**A:** 一小时同一 (用户, 模型) 的 log 通常就几十到几百条,SUM 一次几毫秒。而且大部分场景每小时只算一次(整桶写完盖印章 24h 内不重复算),开销可控。

### Q5:那死信队列会不会越来越大?

**A:** 生产正常时 `XLEN` 应该长期是 0。有值 = 系统告诉你"我需要人来看看"。处理完清空即可。

### Q6:如果死信队列里的消息不处理,数据会永远错?

**A:** 不一定。因为 logs 表(明细账)始终是 Source of Truth。只要根因修好,Backfill 迟早会扫到那条 log,重新走一遍完整流程,quota_data 会自动收敛。死信队列里的消息更多是"排查线索",不是"必须回放的数据"。

---

## 一句话记住 QuotaStream 的设计精神

> **明细账是真理,汇总账靠重算,重算靠幂等,漏投靠扫描,卡壳靠顶班,搞不定就报警。**
