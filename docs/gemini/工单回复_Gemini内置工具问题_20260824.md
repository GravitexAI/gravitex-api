## 一、经核验可正常使用的能力



### 1.1 `urlContext` 与 `googleSearch` 组合

实测请求 `tools: [{"googleSearch": {}}, {"urlContext": {}}]`：


| 观测项                                                                         | 结果                                                                                                     |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| HTTP 状态                                                                     | 200                                                                                                    |
| 是否出现 `Multiple tools are supported only when they are all search tools` 类拒绝 | 否                                                                                                      |
| `groundingMetadata`                                                         | 正常返回                                                                                                   |
| `groundingMetadata.webSearchQueries`                                        | 正常返回                                                                                                   |
| `groundingMetadata.groundingChunks[].web.uri`                               | 正常返回真实链接，如 `https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQHAkDNztktbYFJCGei6-…` |


两个内置工具可在同一请求中被同时受理。抓取结果的限制另见 2.2。

### 1.2 请求与响应的透传保真


| 核验项                                                                  | 结果                                                                                    |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `contents[].parts[].text`（含引号内容）                                     | 逐字节保真。发送 `"REVOLUT LTD" "08804411" Companies House`，模型原样回显，无字面反斜杠                     |
| `tools` 整块（含 `googleSearch` / `urlContext` / `functionDeclarations`） | 原样整块透传                                                                                |
| `functionDeclarations[].parametersJsonSchema`                        | 完整保留                                                                                  |
| `toolConfig` 各子字段                                                    | 完整保留，camelCase 与 snake_case 两种命名法均受理                                                  |
| 响应侧                                                                  | **原生 Gemini 端点为字节级透传** —— 上游返回什么即原样下发，仅旁路解析 `usageMetadata` 用于计费；流式为每个 SSE chunk 原样转发 |


因此 `urlContextMetadata`、`toolCall` / `toolResponse`、完整 `groundingMetadata` 等字段，只要上游返回，调用方一定能收到。报告第三节提出的"根治方案：请求与响应均改为字节级透传"，在响应侧当前即已如此。

### 1.3 版本路径与鉴权


| 核验项                                       | 结果                    |
| ----------------------------------------- | --------------------- |
| `/v1beta/models/{model}:generateContent`  | HTTP 200              |
| `/v1beta1/models/{model}:generateContent` | HTTP 200              |
| 流式 `:streamGenerateContent?alt=sse`       | HTTP 200，正常收到 SSE 事件流 |
| `x-goog-api-key` 请求头鉴权 / `?key=` 查询参数鉴权   | 两种方式在两种版本路径上均可用       |


说明：`v1beta` 是 Gemini Developer API 对预览接口的命名，`v1beta1` 是 Google Cloud 侧对同一预览面的命名。两种写法平台均受理，调用方按任一习惯书写都可，向上游使用哪个版本由平台按后端自动匹配。

## 二、受上游能力边界限制的两项

以下两项**不在转发环节**。平台已确认请求字段完整送达上游、响应字节级原样回传；这两项能力在当前 Gemini 后端本身不具备，因此无论请求如何构造都无法产生上游不提供的输出。

### 2.1 `toolConfig.includeServerSideToolInvocations` 与 `toolCall` / `toolResponse` 事件

**这项能力是什么**：Google 官方称为 **tool context circulation**（工具上下文回流）。开启后响应 parts 中会出现 `toolCall` / `toolResponse` 等部件，携带 `id`、`tool_type`、`thought_signature`，使模型能在后续轮次看到内置工具的真实结果。当前状态为 **Preview，且仅支持 Gemini 3 系模型**。

— [https://ai.google.dev/gemini-api/docs/generate-content/tool-combination](https://ai.google.dev/gemini-api/docs/generate-content/tool-combination)

**实测结果**（`tools: [{"googleSearch": {}}]` + `toolConfig: {"includeServerSideToolInvocations": true}`）：


| 观测项                                  | 结果                                    |
| ------------------------------------ | ------------------------------------- |
| HTTP 状态                              | **200**（请求被正常受理，无报错）                  |
| `candidates[].content.parts[]` 的字段组成 | `["text", "thoughtSignature"]`        |
| 是否出现 `toolCall` / `toolResponse`     | **否**                                 |
| `groundingMetadata.groundingChunks`  | 有，`web.uri` 为真实 grounding redirect 链接 |


即：**上游对该开关是「受理后不生效」而非报错拒绝**。这正是报告中"HTTP 200、搜索有结果，但完全没有事件部件"现象的直接来源 —— 请求本身没有任何问题。

> 提示：验证该开关是否生效，只看 HTTP 状态码会误判，需检查 `candidates[].content.parts[]` 中是否真的出现 `toolCall` / `toolResponse`。

**依据一** —— Spring AI 官方文档（Google GenAI Chat，"Server-Side Tool Invocations"章节）原文：

> Setting `includeServerSideToolInvocations(true)` makes the API include the server's tool calls and responses in the response content, allowing you to observe what the model searched for and what results it received.
>
> **This feature is only supported with the Gemini Developer API (MLDev / API key authentication). It is not supported on Vertex AI.**

— [https://docs.spring.io/spring-ai/reference/api/chat/google-genai-chat.html](https://docs.spring.io/spring-ai/reference/api/chat/google-genai-chat.html)

**依据二** —— Vercel AI SDK 仓库 issue，标题即「Vertex rejects `tool_config.includeServerSideToolInvocations` on gemini-3-flash-preview with function tools」：

> ```
> POST https://aiplatform.googleapis.com/v1/publishers/google/models/gemini-3-flash-preview:streamGenerateContent?alt=sse
> 400 INVALID_ARGUMENT
> Invalid JSON payload received. Unknown name "includeServerSideToolInvocations" at 'tool_config': Cannot find field.
> ```
>
> Only affects Vertex (`@ai-sdk/google-vertex`) — Google AI Studio (`@ai-sdk/google` direct) may not be affected since it targets a different endpoint.

该 issue 的处理结论是「从请求中移除该字段，等 Google 补齐 API 支持」。

— [https://github.com/vercel/ai/issues/14655](https://github.com/vercel/ai/issues/14655)

**关联现象（场景②：模型传入编造的 URL）** 与本项同根因 —— 缺少事件回流，模型看不到 model-visible 的搜索结果。该组合本身在当前后端亦不受支持，Google Cloud 官方文档原文：

> **工具组合**：Gemini API 不支持在同一 `generateContent` 请求中将搜索工具（例如 `googleSearch`）与非搜索工具（例如函数调用或 RAG Engine `retrieval` 工具）相结合。**只有当所有工具均为搜索工具时，才支持多种工具。**

— [https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/grounding-with-google-search](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/grounding-with-google-search)

而 Gemini Developer API 侧文档写的是相反的：

> Gemini 3 models also support combining these built-in tools with custom tools (function calling).

— [https://ai.google.dev/gemini-api/docs/google-search](https://ai.google.dev/gemini-api/docs/google-search)

**替代方案**：终端客户场景②真正需要的是"真实的 grounding redirect 链接"。该链接其实**就在响应里** —— `candidates[].groundingMetadata.groundingChunks[].web.uri`，实测已取到完整链接。由应用层从该字段读取后再调用自身函数即可，不必依赖模型传递。仅"要求模型在同一轮内把链接作为参数传给自定义函数"这一形态才依赖上述受限能力。

### 2.2 URL Context 读取 Google 搜索返回的 redirect 链接

**同一平台、同一模型、同一天的对照实测**：


| 场景                                      | `urlContextMetadata`     | `urlRetrievalStatus`           | 模型行为                                                                                                    |
| --------------------------------------- | ------------------------ | ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `urlContext` 单独使用，抓取普通公开网址              | ✅ 有（`retrievedUrl` 为该网址） | `URL_RETRIEVAL_STATUS_SUCCESS` | 正常返回页面内容                                                                                                |
| `urlContext` + `googleSearch` 组合，抓取搜索结果 | ❌ 无                      | —                              | 模型自述：*"no page content was returned… I'm sorry. I'm not able to access the website(s) you've provided"* |


两条对照可定性：**URL Context 工具本身工作正常**；失败特定于「抓取 Google 搜索返回的 `vertexaisearch.cloud.google.com/grounding-api-redirect/...` 重定向链接」。模型自述的措辞与报告中的 "unable to access the website" 完全一致。

**社区依据** —— Google 官方 SDK 仓库 issue，标题为「Unable to load content using `URL context` for URLs retrieved with `Grounding with Google Search`」：

> The URLs retrieved from search results are in `grounding-api-redirect` format … the `browse` tool cannot track redirected URLs to retrieve the content.
>
> 返回的链接形如 `https://vertexaisearch.cloud.google.com/grounding-api-redirect/[encoded-string]`，而非直接的目标网址。**当报告者在提示中手动给出重定向后的最终目标 URL 时，URL Context 工具即可正常工作。**

— [https://github.com/googleapis/python-genai/issues/1322](https://github.com/googleapis/python-genai/issues/1322)

> 说明：上述原因分析出自该 issue 报告者（其引述了模型的自述），并非 Google 官方声明；但"换成最终目标 URL 即正常"这一现象可复现，与本次对照实测互相印证。

另一条同源 issue（已被 Google 标记 `type: bug` / `priority: p2`）记录了该组合在不同后端下的行为差异：[https://github.com/googleapis/python-genai/issues/941](https://github.com/googleapis/python-genai/issues/941)

**替代方案**（应用层两轮调用，每一步都在 Google 已支持的能力范围内）：

1. 第一轮只启用 `googleSearch`，从 `groundingMetadata.groundingChunks[].web.uri` 取出 grounding redirect 链接；
2. 应用层对该链接做一次 HTTP 重定向解析，得到最终目标 URL；
3. 第二轮把**最终目标 URL** 作为 `urlContext` 的输入发起请求 —— 此时可稳定得到 `URL_RETRIEVAL_STATUS_SUCCESS`。

## 三、病灶 3（请求体双重转义）：专项对照实验结论

报告推断 `webSearchQueries` 中的字面反斜杠源于请求体被二次 JSON 转义。我们针对该现象做了两组对照实验。

**实验一 —— 请求文本是否干净到达模型**


| 项        | 内容                                         |
| -------- | ------------------------------------------ |
| 发送的文本    | `"REVOLUT LTD" "08804411" Companies House` |
| 模型原样回显   | `"REVOLUT LTD" "08804411" Companies House` |
| 是否含字面反斜杠 | **否**                                      |


请求文本逐字节保真到达模型，转发环节未做二次转义。

**实验二 —— 同一请求重复采样，观察模型自拟的搜索串**

固定同一条包含引号的提示，重复请求 6 次，`webSearchQueries` 出现了三种不同取值：


| 形态           | 实例                                             |
| ------------ | ---------------------------------------------- |
| 标准双引号（与输入一致） | `"REVOLUT LTD" "08804411" Companies House`     |
| 引号被模型省略      | `REVOLUT LTD 08804411 Companies House`         |
| 带字面反斜杠       | `\"REVOLUT LTD\" \"08804411\" Companies House` |


**结论**：输入侧已证明保真，输出侧却出现三种形态 —— 因此 `webSearchQueries` 中的字面反斜杠是**模型在组装搜索查询时的非确定性行为**，与转发环节的编码处理无关。该现象具有随机性，单次采样容易被误判为稳定缺陷。

**关于定位方法的一点补充**：报告提到「用渠道 Key 绕过己方全部网关、直接请求 `https://cloud.dataeyes.ai`」。这一步排除的是终端客户自身的链路，请求仍会经过贵方平台的转发层，因此该测试尚未把贵方转发层排除在外。若希望进一步收敛，建议：

1. 贵方开启该渠道的请求体日志，比对**转发给我们之前**的 `contents[].parts[].text` 取值；
2. 或用贵方渠道 Key 直接请求我们的平台入口（完全绕过贵方转发层），用与终端客户逐字节一致的请求体比对现象；
3. 我们这侧可按需开启入口请求体日志，与贵方日志对齐时间戳做双向比对。

## 四、原验收用例的逐条对应



### 用例一：`googleSearch` + `urlContext`


| 原通过标准                                                                        | 实测结论                        |
| ---------------------------------------------------------------------------- | --------------------------- |
| ① HTTP 200                                                                   | ✅ 达成                        |
| ② parts 出现 `toolCall` / `toolResponse`（`GOOGLE_SEARCH_WEB` / `URL_CONTEXT`）  | ⚠️ 受上游限制（2.1）               |
| ③ `urlContextMetadata` 且 `urlRetrievalStatus = URL_RETRIEVAL_STATUS_SUCCESS` | ⚠️ 组合场景受上游限制；可用 2.2 的两轮方案达成 |
| ④ `webSearchQueries` 不含字面反斜杠                                                 | ✅ 转发环节保真；模型侧存在非确定性（第三节）     |




### 用例二：`googleSearch` + `functionDeclarations`


| 原通过标准                                                | 实测结论                                          |
| ---------------------------------------------------- | --------------------------------------------- |
| ① 出现一次 `GOOGLE_SEARCH_WEB` 的 toolCall / toolResponse | ⚠️ 受上游限制（2.1）                                 |
| ② `functionCall` 的 `grounding_uri` 为真实 redirect 链接   | ⚠️ 受上游限制；链接可由应用层从 `groundingChunks` 读取（2.1 末） |
| ③ `webSearchQueries` 不含字面反斜杠                         | ✅ 同上                                          |


**若业务上必须完整满足这两个用例**（尤其是服务端工具事件与「内置工具 + 自定义函数」组合），需要接入具备该能力的 Gemini Developer API 通道。我们的 Gemini 原生端点在该通道下为全链路透传，可直接承载全部通过标准。如有需要可另行沟通接入方案。
