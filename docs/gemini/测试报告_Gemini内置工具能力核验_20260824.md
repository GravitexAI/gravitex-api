# Gemini 内置工具能力核验 —— 测试报告

- 测试日期：2026-08-24
- 测试接口：`https://api.gravitex.ai`
- 测试模型：`gemini-3.7-flash`

## 二、通过项明细



### T-01 / T-02 端点与版本路径


| 请求                                                      | 结果                         |
| ------------------------------------------------------- | -------------------------- |
| `POST /v1beta/models/gemini-3.7-flash:generateContent`  | HTTP 200，正常返回 `candidates` |
| `POST /v1beta1/models/gemini-3.7-flash:generateContent` | HTTP 200，正常返回 `candidates` |


说明：`v1beta` 是 Gemini Developer API 对预览接口的命名，`v1beta1` 是 Google Cloud 侧对同一预览面的命名。平台**两种写法均受理**，调用方按任一习惯书写都可用，向上游使用哪个版本由平台自动匹配后端，调用方无需关心。

### T-03 版本路径的鉴权行为

不携带任何凭证请求 `/v1beta1/models/...`，返回 **HTTP 401** 且响应为 JSON 格式的鉴权错误 —— 说明请求已正确进入鉴权环节（而非落到静态页兜底），路径解析与鉴权链路完整。

### T-04 `?key=` 查询参数鉴权

`POST /v1beta1/models/gemini-3.7-flash:generateContent?key=***` → HTTP 200，返回 `candidates`。Google SDK 常用的两种鉴权方式（`x-goog-api-key` 请求头、`key` 查询参数）在两种版本路径上均可用。

### T-05 流式调用

`POST /v1beta1/models/gemini-3.7-flash:streamGenerateContent?alt=sse` → HTTP 200，正常收到 SSE `data:` 事件流。

### T-06 `urlContext` 单独使用

请求：`tools: [{"urlContext": {}}]`，提示中给出一个公开网址。

响应实测：

```json
"urlContextMetadata": {
  "urlMetadata": [
    {
      "retrievedUrl": "https://ai.google.dev/gemini-api/docs/url-context",
      "urlRetrievalStatus": "URL_RETRIEVAL_STATUS_SUCCESS"
    }
  ]
}
```

结论：**URL Context 工具在平台上工作正常**，抓取成功并如实返回 `urlContextMetadata` 与 `URL_RETRIEVAL_STATUS_SUCCESS`。

### T-07 `urlContext` + `googleSearch` 组合被受理

请求：`tools: [{"googleSearch": {}}, {"urlContext": {}}]`，两个内置工具同时启用。


| 观测项                                                                         | 结果                                                                                                     |

| HTTP 状态                                                                     | 200                                                                                                    |
| 是否出现 `Multiple tools are supported only when they are all search tools` 类拒绝 | **否**                                                                                                  |
| `groundingMetadata`                                                         | 正常返回                                                                                                   |
| `groundingMetadata.webSearchQueries`                                        | 正常返回                                                                                                   |
| `groundingMetadata.groundingChunks[].web.uri`                               | 正常返回真实链接，如 `https://vertexaisearch.cloud.google.com/grounding-api-redirect/AUZIYQHAkDNztktbYFJCGei6-…` |


结论：**两个内置工具可在同一请求中被同时受理**，组合调用可用。抓取结果另见 T-08。

### T-09 `toolConfig` 命名兼容

同一请求分别以两种命名法发送，比对结果：


| 写法                                                                       | 结果       |
| ------------------------------------------------------------------------ | -------- |
| `toolConfig: {"includeServerSideToolInvocations": true}`（camelCase）      | HTTP 200 |
| `toolConfig: {"include_server_side_tool_invocations": true}`（snake_case） | HTTP 200 |


结论：两种命名法行为一致，平台均完整受理并转发。`function_calling_config` / `retrieval_config` 同样兼容。

### T-10 含引号文本的请求体保真透传

请求文本：`Echo this line back verbatim, nothing else:\n"REVOLUT LTD" "08804411" Companies House`

模型回显（原样，未经加工）：

```
"REVOLUT LTD" "08804411" Companies House
```

结论：**含引号内容逐字节保真**，模型收到的是标准双引号，未出现任何字面反斜杠。

同时核验请求体其他关键字段的透传完整性：


| 字段                                                                   | 结果   |
| -------------------------------------------------------------------- | ---- |
| `tools` 整块（含 `googleSearch` / `urlContext` / `functionDeclarations`） | 原样透传 |
| `functionDeclarations[].parametersJsonSchema`                        | 完整保留 |
| `toolConfig` 各子字段                                                    | 完整保留 |


补充说明平台的响应侧机制：**Gemini 原生端点的响应为字节级透传** —— 上游返回什么即原样下发，仅旁路解析 `usageMetadata` 用于计费；流式为每个 SSE chunk 原样转发。因此 `urlContextMetadata`、`toolCall` / `toolResponse`、完整 `groundingMetadata` 等字段，只要上游返回，调用方一定能收到。

## 三、受上游能力限制的两项（附官方依据）

以下两项**不是平台转发环节的问题**。平台已确认请求字段完整送达上游、响应字节级原样回传；这两项能力在当前 Gemini 后端本身不具备，因此无论请求如何构造都无法产生上游不提供的输出。

### T-11 服务端工具事件（`toolCall` / `toolResponse`）

**这项能力是什么**：Google 官方文档称为 **tool context circulation**（工具上下文回流）。开启 `includeServerSideToolInvocations` 后，响应 parts 中会出现 `toolCall` / `toolResponse`（内置工具的调用与返回）等部件，携带 `id`、`tool_type`、`thought_signature`，用于让模型在后续轮次中看到内置工具的真实结果。当前状态为 **Preview，且仅支持 Gemini 3 系模型**。

— [https://ai.google.dev/gemini-api/docs/generate-content/tool-combination](https://ai.google.dev/gemini-api/docs/generate-content/tool-combination)

**实测结果**：请求 `tools: [{"googleSearch": {}}]` + `toolConfig: {"includeServerSideToolInvocations": true}`


| 观测项                                  | 结果                                    |
| ------------------------------------ | ------------------------------------- |
| HTTP 状态                              | **200**（请求被正常受理，无报错）                  |
| `candidates[].content.parts[]` 的字段组成 | `["text", "thoughtSignature"]`        |
| 是否出现 `toolCall`                      | **否**                                 |
| 是否出现 `toolResponse`                  | **否**                                 |
| `groundingMetadata.groundingChunks`  | 有，`web.uri` 为真实 grounding redirect 链接 |


即：**上游对该开关是「受理后不生效」而非报错拒绝**。这解释了"HTTP 200、搜索有结果，但完全没有事件部件"这一现象 —— 请求本身没有问题。

> 提示：验证该开关是否生效，**只看 HTTP 状态码会误判**，需检查 `candidates[].content.parts[]` 中是否真的出现 `toolCall` / `toolResponse`。

**官方与社区依据**：

Spring AI 官方文档（Google GenAI Chat，"Server-Side Tool Invocations"章节）原文：

> Setting `includeServerSideToolInvocations(true)` makes the API include the server's tool calls and responses in the response content, allowing you to observe what the model searched for and what results it received.
>
> **This feature is only supported with the Gemini Developer API (MLDev / API key authentication). It is not supported on Vertex AI.**

— [https://docs.spring.io/spring-ai/reference/api/chat/google-genai-chat.html](https://docs.spring.io/spring-ai/reference/api/chat/google-genai-chat.html)

Vercel AI SDK 仓库 issue，标题即「Vertex rejects `tool_config.includeServerSideToolInvocations` on gemini-3-flash-preview with function tools」：

> ```
> POST https://aiplatform.googleapis.com/v1/publishers/google/models/gemini-3-flash-preview:streamGenerateContent?alt=sse
> 400 INVALID_ARGUMENT
> Invalid JSON payload received. Unknown name "includeServerSideToolInvocations" at 'tool_config': Cannot find field.
> ```
>
> Only affects Vertex (`@ai-sdk/google-vertex`) — Google AI Studio (`@ai-sdk/google` direct) may not be affected since it targets a different endpoint.

该 issue 的结论是「从请求中移除该字段，等 Google 补齐 API 支持」。

— [https://github.com/vercel/ai/issues/14655](https://github.com/vercel/ai/issues/14655)

**同一根因的关联现象**：`googleSearch` + `functionDeclarations`（内置搜索 + 自定义函数）组合下，模型会向自定义函数传入编造的 URL。原因是缺少上述事件回流，模型看不到 model-visible 的搜索结果。该组合在当前后端亦不受支持，Google Cloud 官方文档原文：

> **工具组合**：Gemini API 不支持在同一 `generateContent` 请求中将搜索工具（例如 `googleSearch`）与非搜索工具（例如函数调用或 RAG Engine `retrieval` 工具）相结合。**只有当所有工具均为搜索工具时，才支持多种工具。**

— [https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/grounding-with-google-search](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/grounding/grounding-with-google-search)

**可用的替代方案**：如果业务目标是拿到真实的 grounding redirect 链接，该链接其实**就在响应里** —— `candidates[].groundingMetadata.groundingChunks[].web.uri`，本次实测已取到完整链接。由应用层从该字段读取后再调用自身函数即可，不必依赖模型传递。仅"要求模型在同一轮内把链接作为参数传给自定义函数"这一形态才依赖上述受限能力。

### T-08 组合场景下 URL Context 抓取页面内容

**同一平台、同一模型、同一天的对照实测**：


| 场景                                                 | `urlContextMetadata` | `urlRetrievalStatus`           | 模型行为                                                                                                    |
| -------------------------------------------------- | -------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `urlContext` 单独使用，抓取普通公开网址（T-06）                   | ✅ 有                  | `URL_RETRIEVAL_STATUS_SUCCESS` | 正常返回页面内容                                                                                                |
| `urlContext` + `googleSearch` 组合，抓取搜索结果（T-07/T-08） | ❌ 无                  | —                              | 模型自述：*"no page content was returned… I'm sorry. I'm not able to access the website(s) you've provided"* |


两条对照可定性：**URL Context 工具本身工作正常**；失败特定于「抓取 Google 搜索返回的 `vertexaisearch.cloud.google.com/grounding-api-redirect/...` 重定向链接」。

**社区依据** —— Google 官方 SDK 仓库 issue，标题为「Unable to load content using `URL context` for URLs retrieved with `Grounding with Google Search`」：

> The URLs retrieved from search results are in `grounding-api-redirect` format … the `browse` tool cannot track redirected URLs to retrieve the content.
>
> 返回的链接形如 `https://vertexaisearch.cloud.google.com/grounding-api-redirect/[encoded-string]`，而非直接的目标网址。**当报告者在提示中手动给出重定向后的最终目标 URL 时，URL Context 工具即可正常工作。**

— [https://github.com/googleapis/python-genai/issues/1322](https://github.com/googleapis/python-genai/issues/1322)

> 说明：上述原因分析出自该 issue 报告者（其引述了模型的自述），并非 Google 的官方声明；但"换成最终目标 URL 即正常"这一现象可复现，与本次对照实测互相印证。

另一条同源 issue（已被 Google 标记 `type: bug` / `priority: p2`）也记录了该组合在不同后端下的行为差异：

— [https://github.com/googleapis/python-genai/issues/941](https://github.com/googleapis/python-genai/issues/941)

**可用的替代方案**（应用层两轮调用，每一步都在 Google 已支持的能力范围内）：

1. 第一轮只启用 `googleSearch`，从响应 `groundingMetadata.groundingChunks[].web.uri` 取出 grounding redirect 链接；
2. 应用层对该链接做一次 HTTP 重定向解析，得到最终目标 URL；
3. 第二轮把**最终目标 URL** 作为 `urlContext` 的输入发起请求 —— 此时可稳定得到 `URL_RETRIEVAL_STATUS_SUCCESS`。

## 四、T-12 关于 `webSearchQueries` 中出现字面反斜杠的专项对照

报告中提到 `groundingMetadata.webSearchQueries` 内出现带字面反斜杠的查询串（形如 `\"AIRPAZ SINGAPORE PTE. LTD.\"`），并推断为请求体被二次转义。本次针对该现象做了专项对照实验。

### 实验一：请求文本是否干净到达模型

请求文本包含标准双引号，要求模型原样回显：


| 项        | 内容                                         |
| -------- | ------------------------------------------ |
| 发送的文本    | `"REVOLUT LTD" "08804411" Companies House` |
| 模型回显     | `"REVOLUT LTD" "08804411" Companies House` |
| 是否含字面反斜杠 | **否**                                      |


结论：请求文本**逐字节保真到达模型**，转发环节未做二次转义。

### 实验二：同一请求重复采样，观察模型自拟的搜索串

固定同一条包含引号的提示（`Use Google Search exactly once with this query: "REVOLUT LTD" "08804411" Companies House.`），重复请求 6 次，观察 `webSearchQueries` 的实际取值：


| 出现的取值形态      | 实例                                             |
| ------------ | ---------------------------------------------- |
| 标准双引号（与输入一致） | `"REVOLUT LTD" "08804411" Companies House`     |
| 引号被模型省略      | `REVOLUT LTD 08804411 Companies House`         |
| 带字面反斜杠       | `\"REVOLUT LTD\" \"08804411\" Companies House` |


**同一份输入产生了三种不同取值。**

### 结论

- 输入侧已证明保真（实验一），输出侧却出现三种形态（实验二）；
- 因此 `webSearchQueries` 中的字面反斜杠是**模型在组装搜索查询时的非确定性行为**，与转发环节的编码处理无关；
- 该现象具有随机性，单次采样容易误判为稳定缺陷。

如需进一步排除调用链中其他环节，建议在各环节开启请求体日志，比对同一请求在各跳的 `contents[].parts[].text` 取值。平台侧可按需提供入口请求体日志配合双向比对。
